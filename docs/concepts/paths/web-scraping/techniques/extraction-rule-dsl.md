# Extraction-rule DSL

An extraction rule is a small declarative record: *this field of the output
comes from this place in the page, transformed this way, and here is what it
means if it is not there.* A rule set is the complete statement of how one
page shape becomes one record shape. Holding that statement as **data** — not
as extraction code — is the decision everything else in this subject leans
on: data can be form-edited, validated at one door, previewed before commit,
diffed, versioned, and generated by a model under review.

## The rule record

Every rule, regardless of kind, declares:

- **target field** — the output field it populates; the field vocabulary is
  owned by the dataset schema, and the rule references it (one authority for
  field names — a rule set that can invent fields freely will spray variants
  like `price`, `Price`, `price_usd` across harvests);
- **locator** — where in the page the value lives (the kinds below);
- **cardinality** — one value or many; and for "one", *which* one when the
  locator matches several (first, last, or fail-on-ambiguity). Ambiguity
  handling left undeclared becomes "whatever the engine happened to do",
  which changes when the page or the engine does;
- **post-processing** — trim, strip markup, parse number/date, normalize
  whitespace and currency, resolve relative links against the page address.
  A declared, ordered, finite set of transforms — the moment a rule needs
  arbitrary code, it is no longer reviewable by form and belongs to a
  different tier of the system;
- **failure semantics** — see below. This member is mandatory. A rule
  without declared failure semantics has them anyway; they were just chosen
  by accident.

## Locator kinds

Three kinds cover real pages, and they fail differently — which is why the
kind is an explicit, named choice per rule rather than an implementation
detail:

1. **Structural selector** — a query over the parsed markup tree (the
   selector idiom every markup ecosystem provides). The default kind: it
   reads the page the way its author structured it. Fragile against
   redesigns; robust against copy changes. Prefer selectors anchored to
   *semantic* hooks (stable ids, labeled regions, data attributes) over
   positional chains (`third list, second item`) — positional selectors
   break under the smallest layout edit and, worse, can keep matching the
   *wrong* element, which no failure semantics can catch.
2. **Text pattern** — a regular expression over text content. For values
   with strong internal shape (prices, codes, coordinates, dates) embedded
   in prose, or pages whose markup is too churned to anchor in. Robust
   against restyling; fragile against rewording; and a pattern that matches
   too broadly extracts *wrong* data silently, so patterns carry anchors and
   capture exactly one group.
3. **Structural pointer** — a path into a machine-readable island the page
   embeds: structured-data annotations, a state blob the page ships to its
   own scripts, an attribute payload. When present, the island is the
   *closest thing the page has to an API* — typed, stable across restyles,
   often richer than the rendering. Check for islands **first**; a pointer
   rule outlives a hundred selector rules. Its failure mode is wholesale:
   the island moves or vanishes and every pointer rule dies together —
   loudly, which is the good way to die.

A mature rule set mixes kinds per field deliberately — and may declare a
**fallback chain** (pointer, else selector, else pattern) per field, with
the chain order authored, not improvised by the engine.

## Failure semantics — the mandatory member

What does it mean when the locator matches nothing?

- **required** — the record is invalid without this field. A miss fails the
  *record*; a miss across the whole harvest is a shape-change signal (see
  [shape-change-detection](shape-change-detection.md)). Every rule set
  declares at least one required field, or collapse is indistinguishable
  from a quiet day — the failure-not-empty-success law applied at the rule
  level.
- **optional** — absence is a legitimate state of the source; the field is
  empty and *marked absent*, never silently defaulted to a value that looks
  harvested.
- **defaulted** — absence maps to a declared constant. Legitimate, rare, and
  always visible in the rule, because a default is a claim about the world
  ("no badge means zero") that reviewers must be able to see and argue with.

Matching is only half; the declared post-processing can also fail (a "price"
that will not parse as a number). A coercion failure on a required field
fails the record just as a miss does — a record with a garbage value is
worse than a missing record, because nothing downstream will ever look at it
again.

## Flat and editable inside, serialized at the edges

The rule set lives in **one in-memory shape**: flat, explicit, form-editable
— the shape the rule editor binds to, the previewer executes, and the
authoring assistant emits into. Storage and transport encodings (however the
engine or the persistence layer wants them) are derived from that shape **at
the edges only** — serialize on the way out, parse on the way in, in one
place each.

The anti-pattern this kills: the editor holds one representation, the
harvest engine another, and "save" translates between them in scattered
ad-hoc code — so a rule that previews one way executes another, and a new
rule attribute must be threaded through every translation site or it
silently drops. One conversion boundary, round-trip tested (edit → serialize
→ parse → identical rules), is the whole discipline.

## One validation door

Rules are user input, whatever their source — a form, a model, an import.
They pass through **one validation door** before persisting: field exists in
the schema, locator parses, pattern compiles (and is vetted for
pathological backtracking — a scraper that can be hung by a crafted page has
handed the target a denial-of-service lever against itself), transforms are
known, failure semantics declared. The door is shared by every writer;
model-generated rules get no side entrance, and neither does "just this once"
import code. Validation at N call sites is validation minus the site added
next quarter.
