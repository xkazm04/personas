# Integrity and provenance

Cataloged payloads travel between trust domains: generated by tooling,
committed to a repository, seeded into a database at startup, shipped in
releases, sometimes fetched from outside. Integrity answers "is this payload
the bytes its publisher produced"; provenance answers "who produced it, from
what, when". Both are cheap to *have* and notoriously easy to have **in
decoration form** — present, green, and verifying nothing. This technique is
mostly about the difference.

## The manifest binds identity to bytes — one representation, stated

An integrity manifest is a machine-readable record mapping **entry identity →
digest of the entry's canonical representation**. Every design decision lives
in those two clauses:

- **Entry identity** must be the identity verifiers actually hold when they
  check. If verifiers know entries by catalog id, key the manifest by catalog
  id; if by file path, by path — but then relocation breaks verification, so
  choose the identity that survives the artifact's real lifecycle.
- **The canonical representation** must be *stated in the manifest's
  contract*, because "the digest of X" is meaningless until X is pinned:
  whole file bytes? the payload field only? serialized in which key order,
  which encoding, which line endings? Any two tools that answer differently
  will disagree on every digest while both being "correct". Serialization
  canonicalization is where manifest schemes quietly die — a formatter that
  reorders keys changes every hash while changing nothing real.

The manifest is regenerated by one named tool, and that tool is invokable by
anyone who needs to re-derive it — a digest is the definitional stored
derivation, and the recomputation path is part of the scheme, not tribal
knowledge.

## The verifier must read what the manifest hashed

The signature failure of this technique — worth stating as its central law —
is the **decoration gate**: a verifier keyed differently from its manifest.
The reference system measured a complete specimen: the manifest recorded
digests of **whole files, keyed by file path**; the callers handed the
verifier **a label and a payload-only serialization**. The lookup could
never bind. Every adoption passed — **100%, for the gate's entire lifetime**
— because a miss fell through to "no manifest entry, proceed". The gate ran,
returned green, and verified nothing, indefinitely, silently.

[gate-sees-target](../../_laws.md#gate-sees-target), applied twice over:
the verifier must read the *same identity* and the *same representation*
the manifest recorded. And the meta-lesson is about evidence: **a gate is
not known to work because it exists and passes; it is known to work because
it has been seen to fail.** The cheapest proof is a tamper test — flip one
byte in one payload, run the gate, demand red. A gate that has never
produced red on demand is unproven, and an unproven gate that always passes
is indistinguishable from the decoration above. Put the tamper test where
gates are tested, or accept that green means nothing.

## A second layer must have its own input path

Layering verification (a fast check at load, an authoritative check in a
harder-to-tamper tier) is sound — but only if the layers are independent in
the one dimension that matters: **the input path**. A second verifier that
is *handed its input by the first* — receiving the identity and the content
over a call from the layer it is supposed to double-check, never reading
the artifact itself — is a receipt, not a check: two copies of one number,
compared over bytes one party supplied, is one check. The reference
system's legacy audit executed this exactly: zero disagreements in the
full catalog between two "independent" manifests, because the second layer
never opened a file and its verdict was discarded at every call site.
Independence is not about language, process, or binary boundaries; it is
about who fetched the bytes. A second layer earns its name by reading the
target through its own door — or it should be deleted as honestly as any
other decoration (below).

## Mismatch, absence, and could-not-verify are three verdicts

[failure-not-empty-success](../../_laws.md#failure-not-empty-success)
demands the spellings differ:

- **verified** — entry found, digest matched, now;
- **mismatch** — entry found, digest differed: the strongest signal the
  scheme can produce; something changed the bytes after publication;
- **unverifiable** — no manifest entry for this identity, or the manifest
  itself unreadable: the gate *could not run* for this entry.

The decoration gate above existed because verdict 3 was silently folded
into verdict 1. The honest fold direction depends on deployment posture —
a curated built-in catalog may treat *unverifiable* as a build error (the
manifest is generated in the same pipeline, so absence means the pipeline
broke), while a user-extensible catalog treats it as "unsigned entry,
label it so". But **mismatch never folds anywhere**: it is either a block
or a loud, recorded, per-entry warning with the entry quarantined from
silent adoption. A scheme whose mismatch handler is `log-and-continue` at
the seeding door has decided that integrity is telemetry — sometimes a
legitimate decision for first-party content behind other gates, but it
must be *written down as the decision*, counted, and surfaced
([count-carries-predicate](../../_laws.md#count-carries-predicate): "N
entries seeded, M with mismatched digests" is a dashboard line someone
owns, not a debug log line nobody reads).

## Where to verify: at the doors, not in the aisles

Verification belongs at trust-boundary crossings, and the two that matter:

- **Publication/seed time** — when generated or fetched content enters the
  catalog store. This is the cheap, high-leverage door: content is
  verified once, before anything downstream trusts it.
- **Adoption time** — re-verify if the store itself is writable by parties
  other than the seeding door (user-editable catalogs, shared stores).
  For a read-only built-in catalog, seed-time verification plus a
  tamper-evident store is sufficient; re-hashing on every adoption is
  cost without a threat model.

Between the doors, don't scatter ad-hoc re-checks; a payload that passed
the door is trusted *because the doors are the trust architecture*.

## Deleting a gate honestly

The reference system **deleted** its decoration gate after proving it
inert, and the sequence is the reusable part —
[deletion-is-not-repair](../../_laws.md#deletion-is-not-repair) forbids
removing a *working* signal to hide a defect, so the deletion had to earn
its difference from that:

1. **Prove inertness with evidence**: trace every caller, show what each
   actually passes, demonstrate the lookup can never bind — the gate
   verifies nothing today and has verified nothing since introduction.
2. **Verify the callers first**: enumerate every site that invokes the
   gate and every behavior conditioned on its verdict; confirm removing
   it changes no outcome (it always returned green, so nothing downstream
   ever branched).
3. Then delete — removing decoration, not protection — and record the
   autopsy where the next person proposing "add a checksum gate" will
   find it, because the failure was not "we lacked a gate" but "we had a
   gate no one keyed correctly and no one tamper-tested".

The wrong lessons from such an incident are both available: "integrity
gates are useless" (no — *unproven* gates are useless) and "re-add the
same gate, keyed correctly, still without a tamper test" (which restarts
the same clock).

## Provenance rides the same manifest

The manifest is also the natural carrier of provenance: per entry, the
generator/author, source material identity, generation time, and content
version. Provenance is what turns an integrity incident from "a digest
mismatched" into a diagnosis ("all mismatches are entries from generator
run R"). Downstream, the adopted instance's provenance stamp (see
[adoption-lifecycle](adoption-lifecycle.md)) chains to the catalog entry's
provenance — template to instance, publisher to template — giving the
system an unbroken answer to "where did this running thing come from",
which is the question every post-incident review asks first.
