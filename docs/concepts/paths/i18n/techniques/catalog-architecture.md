# Catalog architecture

The catalog is the product's entire voice as one data structure. Its
architecture decides four things: where authors write, how consumers read,
what the build derives, and what happens when a locale lags. Get these four
right and localization is a pipeline; get any wrong and it is a permanent
manual reconciliation project.

## One source catalog, derived locales

Exactly one locale file is **authored as truth** — the source language. Every
other locale is a translation *of it*, key for key. This is
[one-authority-per-vocabulary](../../_laws.md#one-authority-per-vocabulary)
in its largest instance, and the practical consequences are strict:

- A key is born in the source catalog. It appears in other locales only via
  the translation pipeline, never invented locale-side.
- A key dies in the source catalog. Its survival in any other locale is
  drift, and the completeness gate treats it as a failure, not a leftover.
- Copy review happens against the source; translation review happens
  against the pair.

The source catalog is a plain, diffable, human-editable data file organized
as a tree: **top-level sections** (aligned to product areas), nested groups,
leaf strings. The section boundary is load-bearing — it is the unit of lazy
loading, of translation batching, and of review ownership. Choose section
names by product area, not by component, so that a screen's strings cluster
in one section and a section's translator sees coherent context.

## Typed access via codegen

Consumers reference strings as **typed key paths** (`t.section.key`), and
the type tree is *generated from the source catalog* on every build. This
buys three guarantees that stringly-typed lookup (`translate("section.key")`)
cannot:

- **Compile-time drift detection.** Renaming or deleting a key breaks every
  consumer at build time, in the source locale, before any user sees a raw
  key. This is the cheapest completeness gate in the whole subject.
- **Autocomplete as discovery.** Authors find existing strings instead of
  minting near-duplicates; the catalog's reuse rate is a direct function of
  how discoverable it is at the point of writing.
- **Dead-key detection.** A key no consumer references is findable
  mechanically, which is what keeps a decade-old catalog from becoming an
  archaeology site.

The generated type tree, the per-section split files, and any derived index
are build artifacts: regenerated by a named build step, never hand-edited
([derivation-names-recomputation](../../_laws.md#derivation-names-recomputation)).
If the regeneration step is skippable — a fast-path build that bypasses
codegen — then stale derived catalogs are a shippable state, and the
architecture has a hole exactly the width of that shortcut.

Know the boundary of what typed access proves: a type generated *from* the
catalog constrains **consumers against the catalog**, never the catalog
against the domains it must cover. It faithfully encodes whatever is there
— including the hole. Whether the catalog's key space is itself complete is
the [completeness-gates](completeness-gates.md) question, and no artifact
derived from the catalog can answer it.

## Section splitting for lazy loading

The catalog splits into **independently loadable units along section
boundaries**. Each locale × section pair becomes its own chunk; the runtime
loads a section the first time any of its keys is touched, and preloads the
sections the current navigation context declares. The design points:

- **A small always-loaded base**: the sections every screen needs (common
  actions, chrome, notifications, errors) preload unconditionally. Error
  strings belong in the base tier — the moment you need them is the moment
  loading is least reliable.
- **A declared route→sections map**: each navigation destination names the
  sections it needs, so entering a route warms its strings ahead of first
  access rather than paying a visible round-trip per section.
- **A backstop for undeclared access — runtime or static, but one of them.**
  There are two sound designs. *Load-on-access*: a key touch outside the
  declared map loads its section on demand (rendering fallback in the
  interim), so the map is an optimization. *Pure-read resolution*: the
  resolver never starts loads — a defensible choice, because loaders fired
  from inside property access fan out during rendering and can storm
  (every access triggers a load, every load triggers re-renders, every
  re-render accesses more keys). But pure-read **promotes the map to a
  correctness dependency**: an undeclared section renders fallback text
  forever, in every locale, with no signal. That design is only complete
  with a static gate proving every section referenced from source appears
  in the map — the delivery layer's own completeness check, as binding as
  the catalog's.

## Fallback merging

Resolution for a non-source locale is a **per-section deep merge of the
translated section over its source counterpart**. Any key the translation
lacks resolves to source text automatically, at every depth. This gives the
one runtime property the whole subject leans on: **resolution is total** —
no raw keys, no empty strings, no throw — while keeping the gap *visible to
tooling* (the merge knows which keys fell through, and can report them).

Two boundaries to hold:

- Fallback covers *translation lag*, not *structural absence*. A key missing
  from the source catalog itself is a build error, not a fallback case.
- The merge happens at the resolution layer, once — not by shipping
  pre-merged locale files, which would make every gap invisible to runtime
  telemetry and every source copy edit a full re-ship of all locales.

## Module-scope capture is the architecture's known trap

Any consumer that reads the catalog **once at module initialization** and
stores the resolved string has silently opted out of language switching —
and of section lazy-loading. The architecture's answer is lazy resolution
everywhere: consumers hold *keys* (or accessors) and resolve at render or
use time. Where a stable source-language snapshot is genuinely required
(seed data, comparisons in tests), it is taken through a named,
deliberately-chosen door — not by accident of import order — so the sites
that cannot switch language are enumerable.
