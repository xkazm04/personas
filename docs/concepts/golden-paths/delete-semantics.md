## Trigger

- "Add a delete button for X." / "Let the user remove this credential / team / project."
- "What happens to its executions / memories / triggers when the agent is deleted?"
- "Add a `Delete all` / `Clear` / `Purge` / `Reset` control to this panel."
- "This table needs a new child table keyed by `persona_id`."
- "Deleting Y left orphaned rows / a poller still running / a ghost in the sidebar."
- "Warn the user before they revoke this key."

If you are about to type `DELETE FROM`, `ON DELETE CASCADE`, a new `#[tauri::command] fn delete_*`, a `persona_id TEXT NOT NULL` column, `confirm(`, `useState<string | null>` holding a `confirmingId`, or a `setTimeout` that disarms a delete button — you are in this situation.

## The one way

**Deletion is a two-part contract, and neither part is optional.** Server side: every column that names a parent (`persona_id`, `credential_id`, `team_id`, `project_id`) declares its fate **in the DDL** — `REFERENCES parent(id) ON DELETE CASCADE` when the child is owned, `ON DELETE SET NULL` when the child merely references, and for the small set of audit tables that must outlive their subject, an FK-free column **plus an explicit `-- RETAINED BY DESIGN:` comment on that line**. Absence of an FK must never again mean "we didn't think about it". Then write the delete as one `conn.transaction()` that hard-deletes only what the FK graph genuinely cannot reach (polymorphic columns like `persona_events.source_id`), guard it with `#[requires(…)]` **and** a pure `*_forbidden_reason` check for protected/builtin rows, and return a **receipt struct** saying what actually happened — not `bool`. Write the blast-radius query in the same commit, over the same table set, with the same privilege attribute as the delete, and let its probes propagate errors instead of `.unwrap_or(0)` — a query that fails must not render as *"safe to delete"*. Client side: never fire a destructive IPC from a click handler. Route it through **`useConfirmDestructive()` + `<ConfirmDestructiveModal>`**, feed its `blastRadius` slot from that command via `BlastRadiusPanelLazy`, and set `requireTypedConfirmation` whenever the blast radius is non-empty or the entity holds a secret. **Skip the dialog entirely when the blast radius comes back empty** — a confirm the user always clicks through teaches them to always click through. Capture the entity at arm time, re-resolve it against the live collection at confirm time, and disarm the confirm if its context changed underneath. The contract between the halves: **the set of tables the confirm names must be the set the delete touches, and any count it shows must come from the query that will run** — never from `items.length` in the client's store, and never from a narrower `WHERE` than the delete's.

Two things this repo already does that you must not re-derive: `PRAGMA foreign_keys = ON` **is** guaranteed on every pooled connection (`db/src/lib.rs:201`, applied by `SqlitePragmaCustomizer::on_acquire` at `:220-224`), so you may rely on declared cascades and need not hand-delete FK'd children "just in case"; and `ConfirmDialog` (not `ConfirmDestructiveModal`) is the only confirm primitive with an in-flight lock, so until Gap #3 is fixed a destructive confirm must guard its own double-fire.

- **`commands/core/personas.rs:673` `delete_persona`** — the full-strength delete: `mark_deleting` → forbidden-reason guard → cancel running executions → drain with a 15 s deadline → force-cancel → delete → reclaim orphaned disk assets → return a receipt.

  it. `require_privileged` (async) only checks that the IPC session token was

  documentation, not a guard — the attribute plus the `PRIVILEGED_COMMANDS`
  listing is what enforces. See `ipc-command-authorization.md`.

## Steps

**Adding a child table**

1. **Declare the fate in the DDL.** `parent_id TEXT NOT NULL REFERENCES parent(id) ON DELETE CASCADE` for owned data; `ON DELETE SET NULL` (column nullable) when the row is a record of something that happened *to* the parent and should survive it; FK-free **only** for an audit/history table, and then with `-- RETAINED BY DESIGN: <why>` on the column line.
2. **If the table already shipped without an FK**, add a `migrate_<table>` function to `fk_hygiene.rs` and call it from `run()`. Do not hand-roll the rebuild.
3. **Do not add the table to the startup orphan sweep.** See Deviations — that sweep currently lists only tables that already cascade, which is the inverse of useful.

**Writing the delete**

4. **Guard first — twice.** Put `#[requires(privileged)]` on the command (a secret, a device pairing, or anything cross-entity earns `privileged`), **and put the same attribute on the matching `*_blast_radius`** — the preview must never be cheaper to obtain than the action. Then load the entity, run a pure `*_forbidden_reason` check (system/builtin origin, in-use, tier), and return `AppError::Forbidden` before touching anything.
5. **Quiesce the runtime.** If the entity can have live work (executions, pollers, sessions), mark it deleting, cancel, and drain with a deadline before the row goes. `delete_persona` is the reference.
6. **One transaction.** `let tx = conn.transaction()?;` — hard-delete only the polymorphic / FK-unreachable children, then the row, then `tx.commit()`. Never `unchecked_transaction()` on a delete path; it opts out of rusqlite's nesting safety for no gain.
7. **Return a receipt, not `bool`.** A `#[derive(TS)] #[ts(export)]` struct naming what was cancelled, what was force-stopped, what failed. `bool` throws away the only honest thing you can tell the user afterwards.
8. **Write the blast-radius query beside the delete**, in the same repo module, counting exactly the tables the delete will touch — **the same table set and the same `WHERE` clauses**. A narrower predicate in the probe than in the delete (`status = 'active'`, `status IN ('running','queued')`) is a lie by construction. Propagate query errors with `?`; never `.unwrap_or(0)`, which turns a broken probe into a reassuring empty result. Return `Vec<(category, description)>`; register a `<entity>_blast_radius` command next to `delete_<entity>`, with the same privilege attribute.

**Building the confirm**

9. **Fetch before you ask.** In the click handler, call `confirm({ … blastRadius: <BlastRadiusPanelLazy fetcher={() => get<Entity>BlastRadius(id)} /> })`. Capture the entity's id and display name **into the config** at arm time.
10. **Scale the friction to the radius.** Empty radius → skip the dialog. Non-empty, or the entity holds a secret → `requireTypedConfirmation: entity.name`.
11. **Put the real numbers in `details`/`message`.** Any count you show must be the server's count. `tx(t.…confirm_body, { count })` where `count` came from an IPC, never from `list.length`.
12. **Guard the drift.** If the surface can switch entities under an open dialog, either invalidate on identity change (`useQuerySafeMode`) or re-resolve at confirm time (`FleetProcessScanner`). Pick one; do not ship neither.
13. **Await, then reconcile.** `await deleteX(id)` → invalidate in-flight fetches for that id → purge derived state (caches, selection, related sessions) → toast from the **receipt**. Never remove the row optimistically: a delete that the backend refused would leave the UI lying.
14. **Stop.** No `window.confirm`, no arm-and-disarm timer, no second modal shell, no local `*ConfirmDialog` component.

## Anti-patterns

- **A bare `parent_id TEXT NOT NULL` with no `REFERENCES`.** 224 FK-shaped columns repo-wide are in this state and 113 of them name a real table — 44 of those carry an unconstrained `persona_id`, against 35 that cascade it. Nothing cascades them, the orphan sweep covers none of them, and no delete function mentions them. The rows are unreachable from any UI, counted by no retention sweep, and permanent. `teams.rs:320-323` records this exact failure costing every message of every deleted team until 2026-08-09.
- **Orphans that are alive, not merely dead.** `scheduled_retries` (`persona_id TEXT NOT NULL`, no FK) is drained by the event-bus tick; a persona delete cascades away its executions and leaves the retry row pointing at both a dead execution and a dead persona. Same shape for `slack_poll_state` / `discord_poll_state` / `slack_inbound_messages` / `discord_inbound_messages` / `persona_background_job` / `alert_rules` / `fired_alerts`. "Orphan row" understates it: the runtime keeps acting on behalf of something the user deleted.
- **Hand-deleting children that already have an FK** "in case `PRAGMA foreign_keys` isn't on". It is on — `STANDARD_PRAGMAS` (`lib.rs:201`) is applied by the r2d2 customizer on **every acquire**. The hedge costs a statement per child and, worse, teaches the next author that the FK graph cannot be trusted, which is how the 38 un-FK'd tables happened.
- **A blast-radius probe narrower than the delete it previews.** `WHERE deployment_status = 'active'` / `WHERE status IN ('running','queued')` inside a probe whose delete takes every row (`repos/core/personas.rs:1922`, `:1986`). The dialog then reads as an exhaustive impact list while omitting the entire history behind each category.
- **`.unwrap_or(0)` on a blast-radius count.** A failed probe becomes zero, zero becomes an empty list, and an empty list renders as `t.shared.blast_safe_to_delete` — *"No dependent resources found. Safe to delete."* The one failure mode a safety dialog must never have. It has already shipped once (`repos/core/personas.rs:1934-1939`).
- **A preview command less privileged than the action it previews.** `credential_blast_radius` has no guard; `delete_credential` is `#[requires(privileged)]`. An impact enumeration over a secret is reconnaissance, and it must cost at least what the delete costs.
- **A hand-maintained table list as the cleanup mechanism.** There are four: the DDL, each `blast_radius`, `cleanup_orphan_rows`'s `ORPHAN_TABLES` (12 of 35), and `delete_project_children`'s 25-statement const (missing 4). They demonstrably disagree. `cleanup_orphan_rows` is honest about being a belt-and-braces over cascade children — but that is 34% coverage of the population it targets, and 0% of the 44 unconstrained tables that are the only ones which can actually orphan.
- **An FK pointing at a table that does not exist.** `mcp_gateway_members` references `credentials(id)`; the table is `persona_credentials`. Unresolvable FKs cascade nothing and fail at insert.
- **`unchecked_transaction()` on a delete path** — `personas::delete` (`repos/core/personas.rs:1762`). It skips rusqlite's nesting check for no benefit on a path where correctness is the whole point.
- **Returning `bool` from a delete that had side effects.** `delete_credential`, `delete_team`, and 100+ others tell the caller nothing about what they stopped. The UI then invents its own summary.
- **Server-composed English in a blast-radius description.** All three `blast_radius` functions `format!` their strings in Rust (`personas.rs:1930`, `:1952`, `:2009`, `:2056`, `:2079`; `credentials.rs:495`, `:510`). The panel chrome is translated (`t.shared.blast_impact`); the bullets are not. A non-English user gets a translated "Impact" heading over English body text on the most consequential dialog in the app. Emit `(category, count, params)` and let the client render `t.status_tokens…`.
- **A count in the confirm computed on the client.** `MemoriesPageDense.tsx:388` interpolates `memories.length`, but `memories::delete_all` (`repos/core/memories.rs:1052-1058`) runs `DELETE … WHERE tier != 'core'`. The dialog promises to delete pinned memories that will survive. The number in a confirm must come from the query that will run.
- **An eight-idiom confirm layer.** `useConfirmDestructive`, `ConfirmDialog`, `useConfirmClick` (arm-on-first-click), `InlineConfirm` (popover + click-outside), `SkillActionConfirm`, `ActionConfirmModal`, `MutationConfirmBanner`, the arm-*delay* in `PairApprovalModal.tsx:24`, plus a local `confirm<X>Id` + `setTimeout` in 10 more files. **No two of the eight are a superset of one another, and not one provides all three of {typed confirmation, blast radius, in-flight lock}.** Nothing anywhere states which risk class demands which, so the safety a user gets is a function of which file the author was in.
- **Disarm timers as call-site literals.** 450 / 3000 / 3500 / 5000 ms are all in use with no shared constant, plus two arm-by-id sites (`FixtureDropdownList.tsx:19`, `SmeeRelayTab.tsx:53`) that never auto-disarm at all.
- **Inverting the risk ladder.** Deleting an *agent* requires typing its name — the **only** `requireTypedConfirmation` call site in the app (`PersonaOverviewActions.tsx:52`). Deleting a *credential* — a live secret shared by many agents — is one click (`CredentialDeleteDialog.tsx:36-52`). Deleting *every* memory, message or review is also one click.
- **A busy lock defeated by a synchronous handler.** `ConfirmDialog`'s `await Promise.resolve(onConfirm())` (`:43`) yields exactly one microtask when `onConfirm` is sync, then `finally { setBusy(false) }` re-enables the button. At `AssetCard.tsx:315`, `PlaybooksPanel.tsx:196`, `WorkspacesAtlas.tsx:169` and `KpiDetailModal.tsx:100` (`void …then()`, promise discarded) the lock is decorative. **Return the promise from `onConfirm`.**
- **Arming a confirm over a live selection.** `GallerySelectionBar.tsx:20-80` renders the count from current props (`:64`) and calls `onDelete()` with **no argument** (`:60`) — selecting more assets during the 3 s armed window silently changes what the confirmed button deletes, and the label re-renders to match without re-arming. Same shape at `MessageList.tsx:96,302` and `MemoriesPageDense.tsx:54,251`.
- **A disarm timer with no ref and no cleanup.** `AutomationCardActions.tsx:27` fires a bare `setTimeout` inside the click handler; unmounting inside the window sets state on a dead component.
- **Two views of the same entity with opposite safety.** `MemoriesPageDense.tsx:385` gates memory delete behind `ConfirmDialog`; `MemoriesPageGraph.tsx:247` deletes inline with none.
- **Re-implementing `ConfirmDestructiveModal` around a correct `BlastRadiusPanel`.** `AutomationsSection.tsx:202-243` copies the primitive's exact `BaseModal` props, `max-w-sm`, panel class, red icon square and button pair — and thereby loses `requireTypedConfirmation` and the `details` card while gaining nothing.
- **A confirm that outlives its target.** The dialog is armed against entity A; the list re-sorts, the user switches credentials, another session deletes the row, or the OS recycles the PID. Only two files in the repo encode this.
- **Naming a hook after a feature it does not have.** `vault/shared/hooks/useUndoDelete.ts` implements confirm-state only; there is no undo anywhere in it.
- **Re-declaring a ts-rs type by hand.** `src/api/agents/personas.ts:97-100` hand-writes `BlastRadiusItem` while `src/lib/bindings/BlastRadiusItem.ts` is generated and imported by nobody. The generated file is the contract; a new field on the Rust struct would silently never reach the UI.
- **Two components with the same name and different meanings.** `overview/components/BlastRadiusPanel` (server enumeration) and `vault/sub_dependencies/BlastRadiusPanel` (client graph-derived, with a `severity` bucket). Import-time ambiguity on the exact primitive this path mandates.

### No reversal anywhere

There is no post-delete undo, no trash, and no recycle bin for personas, credentials, memories, messages, triggers, teams, or research entities. `vault/shared/hooks/useUndoDelete.ts` is confirm-state only and its exported type is `UndoDeleteState` — an actively misleading name. Real undo exists in the repo but never for a delete: `undo_execution` (`DataDiffSection.tsx:90-100`), the triage `UndoChip` (`useUnifiedTriage.ts:436`, which honestly refuses when no reverse door exists — `triageDispatch.ts:316-339`), the editor's Ctrl+Z stack, and media-studio history. Archive/restore exists for personas (`api/agents/personas.ts:82,86`, wired at `PersonaOverviewActions.tsx:151,175`) and memories (`MemoryCard.tsx:136-141`) — but hard delete sits beside archive and is irreversible. The only "trash" is the OS one (`plugins/drive/components/DriveTrashBanner.tsx:16-34`). **Every confirm in this app is the only line of defence**, which is why the layer's inconsistency matters more here than it would elsewhere.

## Gaps in the primitives

1. **The ownership graph is maintained in five hand-written copies, and this is upstream of nearly every deviation above.** SQLite knows the truth — `pragma_foreign_key_list` returns it per table, and `fk_hygiene.rs` already reads exactly that (`:174-182` for idempotency, `:309-317` for a `pragma_foreign_key_check` verification before commit). But the fact is re-encoded by hand in (a) the DDL, (b) each `blast_radius()`'s pile of `COUNT(*)` queries, (c) `cleanup_orphan_rows`'s 12-name array, (d) `delete_project_children`'s 25-statement const, and (e) each delete's manual child cleanup. Five copies, no reconciliation, and they demonstrably disagree: the sweep names 12 of 35, the blast radius omits 26 of 35, `delete_project_children` omits 4, and 44 tables appear in none of them. **A schema-derived blast radius — walk `pragma_foreign_key_list` transitively from the parent, `COUNT(*)` per child, label via a `table → category` map — would make (b), (c), (d) and the missing 110 commands fall out for free, second-order cascades included.** Everything else in this section is a consequence of not having done that. `fk_hygiene.rs` is proof the machinery is already in the codebase; it is used only to *write* FKs, never to *read* the graph back.
2. **`blast_radius` returns prose, not data.** `Vec<(String, String)>` where the second element is a `format!`-composed English sentence. There is no count, no severity, no table name — so the client cannot translate it, sort it, threshold it, or decide whether to require typed confirmation from it. `BlastRadiusItem { category, description }` should be `{ category, table, count, severity }` with rendering client-side.
3. **`ConfirmDestructiveModal` has no in-flight lock, and `ConfirmDialog`'s can be defeated by the caller.** `useConfirmDestructive`'s `onConfirm` (`:204-207`) calls the caller's handler and closes the modal in the same synchronous tick, before any await resolves — the *more* destructive primitive is the *less* protected one. Meanwhile `ConfirmDialog`'s `busy` depends on `onConfirm` **returning** a promise (`:43`); four of its 21 call sites pass a sync or `void`-discarded handler and get a decorative lock. The signature should be `onConfirm: () => Promise<void>` so the type system asks for the thing the lock needs. `PairApprovalModal` is the only surface with a lock that cannot be defeated.
4. **Neither confirm primitive encodes context drift.** The hard part both scouts named independently has two correct implementations in the repo (`useQuerySafeMode`, `FleetProcessScanner`) and zero in the shared layer. `useConfirmDestructive` should take an `entityKey` and a `resolve: () => T | undefined`, auto-dismissing when the key changes and re-resolving before firing `onConfirm`.
5. **No blast-radius-aware defaulting.** The proportionality rule (empty radius → no dialog; non-empty → typed confirmation) exists once, hand-written, in `useCapabilityToggle`. `useConfirmDestructive` cannot express it because the `blastRadius` slot is an opaque `ReactNode` the hook never sees the contents of. Passing `blastRadius` as *data* (Gap #2) rather than a node makes the rule enforceable in the primitive.
6. **No stated risk ladder.** Nothing in the repo says which class of destructive action earns which idiom. The observable result is inverted: agents need a typed name, credentials do not; `delete_all_*` needs neither. A three-rung ladder — *reversible/bounded → `ConfirmDialog`; irreversible with dependents → `ConfirmDestructiveModal` + blast radius; irreversible + secret or fleet-wide → also `requireTypedConfirmation`* — is one paragraph in `.claude/Design.md` and would settle the whole layer.
7. **Deletes return `bool`.** Only `delete_persona` returns a receipt; `bulk_delete_personas` returns per-id outcomes. Everything else returns `bool` or `usize`, so the UI can only say "Deleted." A `DeleteResult { deleted, stopped, retained, warnings }` shape reusable across commands is missing.
8. **No reversal primitive.** No trash, no undo toast, and the only `deleted_at` column in the schema belongs to the inert `persona_tombstones` — there is no soft delete anywhere (0 `is_deleted`, 0 `archived_at`, 0 `status='deleted'`, 0 `lifecycle='deleted'`). Archive/restore exists for personas and memories but sits *beside* hard delete rather than in front of it. See **No reversal anywhere** above; the consequence is that every confirm in this app is the only line of defence.
9. **`fk_hygiene.rs` has no "what still needs retrofitting" report.** It migrates a hardcoded list of 9 tables (`:16-27`) and does it very well — `FkDisabledGuard` taken in autocommit *before* the transaction (`:191`, because `PRAGMA foreign_keys` is a documented no-op inside one, which previously let a `DROP TABLE` fire other tables' cascades and wipe child rows on upgrade), a row-count-verified copy that refuses to swap on mismatch (`:275-280`), and a `pragma_foreign_key_check` gate before commit (`:309-317`). It already holds the machinery to *enumerate* the 113 unconstrained-but-resolvable columns, and never does.
10. **Protection is a persona-only concept.** `deletion_forbidden_reason` exists for `trust_origin == System` and nothing else. `is_builtin` on tool and connector definitions is checked only on import/export. There is no shared `Protected` trait, no `is_protected(&self) -> Option<Reason>` on the model layer, so every new entity type starts unprotected by default.
11. **No row-level authorization primitive.** `crud_delete!` (`db/src/macros.rs:209-220`) hardcodes `WHERE id = ?1`. Session-level guards exist and are well adopted (108 of 115); ownership guards do not exist at all. This is a correct trade for a single-user desktop app and an undeclared landmine for the shared-workspace future the repo is otherwise building toward.
12. **Zero enforcement.** 21 custom ESLint rules; none covers destructive actions. `npm run check` runs `check:contracts`, which already parses `lib.rs`'s invoke handler and every `#[tauri::command]` — and checks nothing about deletes. See below.

## The missing gate

Everything in Deviations shipped green. The mechanism of that greenness is worth naming precisely, because it is the section-9 pathology in its purest form: this situation already has three artifacts that *look* like coverage and cannot fail for the reason they exist — a test literally called `test_delete_cascade_is_complete` that samples 2 of ~49 reachable tables, a startup sweep covering 12 of 35 cascade children and 0 of the 44 tables that can actually orphan, and a feature doc asserting *"deleting a persona cascades cleanly."* Add to that five blast-radius probes that `.unwrap_or(0)` a failed query into the words "Safe to delete." **The problem here is not missing gates; it is four artifacts manufacturing confidence.** Three gates, one per half plus one for the seam.

### Gate A (server) — schema-derived cascade completeness

- **Signal.** Any column named `<entity>_id` on a table in `personas.db`, where `<entity>` resolves to a real table. Near-perfect because it is read from the *live database*, not from source text: `pragma_table_info(t)` gives the columns, `pragma_foreign_key_list(t)` gives the declared FKs, so "has a parent-shaped column but no FK to that parent" is a two-pragma join. `fk_hygiene.rs:34-56,174-182` already performs exactly these reads, so this is a use of existing machinery, not new infrastructure. It also self-corrects for the 111 polymorphic columns (`source_id`, `entity_id`, `model_id`) whose prefix names no table — they simply do not resolve.
- **Mechanism.** A Rust `#[test]` in `db/src/migrations/` (runs in `npm run test:rust`, already CI-gated) over `init_test_db()`, with four assertions:
  1. Every resolvable parent-shaped column without an FK appears in a `RETAINED_WITHOUT_FK` const allowlist. **Fails today on ~113 columns.**
  2. Every declared FK resolves to a table that exists. **Fails today on `mcp_gateway_members`'s two `credentials(id)` references.**
  3. Every FK on a table reachable from a registered `delete_*` command declares an explicit `ON DELETE` action. **Fails today on `template_feedback.review_id`'s implicit `NO ACTION`.**
  4. Every table in `cleanup_orphan_rows::ORPHAN_TABLES` still exists, and the sweep either covers all 35 cascade children or is renamed to say it is a sample. **Fails today at 12 of 35.**
- **Allowlist.** The audit/history tables where outliving the subject is the point, each with a one-line reason beside it: `credential_audit_log`, `api_key_audit`, `provider_audit_log`, `tool_execution_audit_log`, `healing_audit_log`, `audit_incidents`, `cli_session_read_audit`, `persona_change_log`, `adoption_log`, `deployment_history`, plus `persona_tombstones` (must survive its subject by construction). Everything else in today's 44 unconstrained `persona_id` tables is a bug, not an exception. Adding a table to the allowlist is a reviewable diff; adding a bare `persona_id` is currently invisible.
- **How it fails loudly if its precondition is absent.** The failure mode of a pragma-driven test is a *silent empty set* — a renamed pragma, a schema that didn't migrate, a pool missing the parent table, and the loop iterates zero times and passes. So the test asserts floors first: `assert!(tables_scanned >= 200 && fk_edges >= 150 && parent_shaped_columns >= 200, "cascade audit scanned {tables_scanned} tables / {fk_edges} FKs — the introspection is broken, not the schema")`. Measured against today's DB those are ~239 tables, 197 FK clauses and 224 parent-shaped columns, so the floors sit comfortably below reality and far above a broken read. Same for the allowlist: `assert!(!RETAINED_WITHOUT_FK.is_empty())` plus a check that every entry still names an existing table, so an exemption that outlives its table fails instead of silently widening.

### Gate B (the seam) — blast radius must describe the delete

The gate nobody has, and the one the whole leaf turns on.

- **Signal.** A registered `<entity>_blast_radius` command paired with a `delete_<entity>`. Three exist; the pairing is a naming convention the handler list already exposes.
- **Mechanism.** A Rust `#[test]` per pair, in the same module as the repo functions: seed a parent with one row in **every** table Gate A's FK walk reports as reachable from it (first- *and* second-order), call `blast_radius`, call `delete`, then assert (a) every table that lost rows is named by at least one returned `category`, and (b) every returned count equals the number of rows the delete actually removed from that table. This is what `test_delete_cascade_is_complete` (`commands/core/personas.rs:1078`) was reaching for; the difference is that the table set comes from the pragma walk rather than from the author's memory, so it grows on its own. It fails today for `persona_blast_radius` (26 unreported tables, plus the two narrowed predicates) and `credential_blast_radius` (6), and passes for `automation_blast_radius`.
- **Allowlist.** Categories deliberately aggregated (e.g. three trigger kinds under one `trigger` label) declare their table set explicitly in the test fixture. Nothing else is exempt: if a table dies unannounced, that is the defect.
- **How it fails loudly if its precondition is absent.** Two ways this could no-op. If the seeder inserts nothing, the delete removes nothing and every assertion is vacuous — so assert `rows_before > 0` per table *and* `tables_seeded == tables_from_pragma_walk` before touching the delete. If `blast_radius` swallows an error into `.unwrap_or(0)` (as all five probes do today), a broken query passes as a correct zero — so the test additionally asserts a **non-empty** result for a parent that demonstrably has children, which is precisely the regression that shipped once already (`repos/core/personas.rs:1934-1939`). Fix the `.unwrap_or(0)`s and this second guard becomes redundant; until then it is the only thing standing between a failed probe and the words *"Safe to delete."*

### Gate C (client) — every destructive command has a confirm, and every preview costs what its delete costs

- **Signal.** The command name. `check-command-contract.mjs` already extracts every registered command from `lib.rs` and every `#[tauri::command]` from the Rust tree; the destructive set is `/(^|_)(delete|remove|purge|clear|wipe|prune|forget|discard|reset|revoke|drop)(_|$)/` over that list — 128 today (113 for the narrow `delete|remove|purge|clear`). It is a *name* check, so no unusual call shape defeats it.
- **Mechanism.** A `check:delete-contract` block inside `scripts/check-command-contract.mjs` — it already owns the `lib.rs` parse, the `src/**` walk and the `process.exit(1)` — wired into `npm run check` beside `check:contracts`. Three assertions: **(1)** every destructive command's `src/api/**` wrapper is referenced only from files that also import a sanctioned confirm primitive, or is allowlisted (**fails today for 52 UI call sites**); **(2)** every destructive command carries a `#[requires(…)]` attribute **and is listed in `PRIVILEGED_COMMANDS`** — a bare `require_auth*` call MUST NOT count as compliance, because both functions are unconditional `Ok(())`; accepting them would certify an unguarded command as guarded (**fails today for 7 with no attribute at all, plus the 40 annotated-but-unlisted commands `ipc-command-authorization.md` enumerates**); **(3)** every `<entity>_blast_radius` carries **at least** the privilege attribute of its `delete_<entity>` (**fails today for `credential_blast_radius`**). Assertion (3) is one comparison and closes a real security hole.
- **Allowlist.** Named, with reasons: leaf-row deletes with no dependents and a trivially reversible effect (`delete_app_setting`, `clear_frontend_crashes`, `artist_clear_autosave`, `clear_pending_oauth`, `companion_daily_goals_discard`), and internal/dev-only commands (`delete_stale_seed_templates`). Seed the allowlist at today's population minus the named parents, then ratchet — the gate's value is that new entries require a diff someone reads.
- **How it fails loudly if its own precondition is absent.** `check-command-contract.mjs` already models the right instinct: it `throw`s when the `invoke_handler` regex misses (`:43`) rather than proceeding over an empty set. The new block inherits that and adds `if (destructive.size < 100) throw new Error(…)` — if a refactor moves the handler block or breaks name extraction, the destructive set collapses toward zero and *every* assertion passes vacuously. That is the exact shape of the `cargo test`-without-`--features desktop` and gitleaks-not-installed failures this repo has already shipped. **A gate over a set must assert the set is populated before it asserts anything about its members.**

**What no gate can catch, and therefore belongs to review:** context drift (Gap #4) is a runtime-ordering property — no static signal distinguishes a confirm that re-resolves its target from one that does not, and the two correct implementations in the repo look nothing alike. Until the guard lives inside `useConfirmDestructive`, "does this confirm survive its entity changing?" is a question for the security-sensitive-edit review checklist, not a linter. That is a finding, not an omission.
