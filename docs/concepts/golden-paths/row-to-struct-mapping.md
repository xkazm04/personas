# Golden path — Row to struct mapping

> Situation node: `data-persistence/repository-access/row-to-struct-mapping` · [situation spine](../situation-spine.md)
> Composed 2026-08-14 from a ground-truth sweep of the whole Rust tree against `master`.
> Sweep size: **963 `.rs` files** (the census walk sees exactly the `rust.files` figure in
> [`shared-facts.json`](../shared-facts.json)) · **793 `query_map` call sites** · **169 named row
> mappers** (125 hand-written `fn row_to_*` + 44 generated by `row_mapper!`) · **137 inline
> struct-building closures**. Every number below was counted by a script
> run against the tree, never estimated; where a heuristic classifier was uncertain the sites were
> opened and read (the 10 it could not classify are named in §7).
> Dimensions: **code-quality · resilience · function**. Server-only; not two-sided.
> A **convergence sweep** was run against five sibling repos (`brainiac` — Rust/sqlx/Postgres;
> `personas-cloud` — TS/better-sqlite3; `personas-web` — TS/Supabase; `vibeman` — TS/better-sqlite3;
> `ascent` — TS/Prisma) to separate physics from local taste. It changed one prescription in this
> document (§5, enum columns) and upgraded two proposals from speculation to precedent. Findings are
> cited inline and summarised in §6.
> Sibling leaves: **[JSON blob column](./json-blob-column.md)** owns what goes *inside* a column and
> its decode policy — this path owns what happens to the **row** when that decode fails, and the two
> interact violently (§8 Gap 1, cross-referenced not duplicated). **[Schema change](./schema-change.md)**
> owns the DDL that the mapper's column names must agree with.
> The **Deviations** section is a fix backlog.

## 1 Trigger

- "Read these rows back into a struct" / "add a `list_*` function to the repo"
- "Add a field to `PersonaExecution` / `DevTask` / `Persona`" — the mapper is the second edit, right after the model
- "One row is corrupt — should the list fail, or should that row disappear?"
- "This list is missing an item but the API returned 200"
- "The column exists in the table but the field comes back `null` in the UI"
- "Why does this status say `failed` when the row says something else?"

If you are about to type `stmt.query_map(`, `fn row_to_`, `row.get(0)`, `row_mapper!(`, `.filter_map(|r| r.ok())`, or `rows.collect::<Result<Vec<_>, _>>()` — you are in this situation.

## 2 The one way

**Write exactly one named `fn row_to_<entity>(row: &Row) -> rusqlite::Result<Entity>` per struct, put it at the top of the repo module that owns the table, address every column by its string name, and let `?` propagate every field error out of the mapper unchanged — a mapper never decides anything.** The *call site* decides, and it has exactly two legal choices, picked by one question: **is a missing row a lie to the user, or a lost job?** A **user-facing list read** propagates — `rows.collect::<Result<Vec<_>, _>>().map_err(AppError::Database)` — because returning `200 OK` with a silently short list is worse than an error the user can retry. A **background sweep, reaper, or batch worker** uses `collect_rows(rows, "<table>::<op>")` from `db/src/repos/utils.rs`, because a row it drops is a job nobody will ever run again, and `collect_rows` is the only thing in the tree that writes that row's index and error into the log. Those two are the whole menu. **Never `filter_map(|r| r.ok())`, never `.flatten()`, never `.unwrap_or_default()` on a collected row set** — all three are "discard the evidence" spelled three ways, and the tree has 179 of them. Then stop: no defaulting inside the mapper, no `unwrap_or` on a column, no positional `row.get(0)`, and no second mapper for the same struct.

### Which clauses are physics, which are this house

Per the [contract](../golden-path-contract.md) and the [portability test](../research/portability-test.md), a
prescription only travels if something else reinvented it. Tagged, so an adopting repo can sort them:

| Clause | Warrant | Evidence |
|---|---|---|
| The mapper is named `row_to_<entity>` | **physics** | independently reinvented in 3 sibling repos across 2 languages and 3 drivers — `brainiac` `fn row_to_document`, `personas-cloud` `rowToPersona`, `vibeman` `rowToPatch` |
| Address columns by name, not position | **physics** | `brainiac` is **601 name-addressed reads to 0 positional** across its whole tree; the three TS siblings are structurally name-only. Nobody else pays the positional cost — **Personas is the outlier here, not the standard** |
| An unknown stored enum token degrades to the **least-privileged / least-terminal** variant, and logs | **physics** | four independent instances: `brainiac` `RevisionPolicy::parse(…).unwrap_or(NeedsReview)`, `personas-web` unknown status → `"running"` + `console.warn`, `ascent` unknown PR state → `"open"`, `ascent` corrupt role → `"member"`. **This corrects §5 below** |
| A mapper propagates; the caller decides the set-level policy | **physics** | the inverse is what fails elsewhere: `brainiac`'s infallible mappers *panic* on a bad row, `personas-cloud`'s `as T` cast emits a malformed object with no error. A mapper that cannot fail has not removed the failure |
| A degraded read must be **surfaced**, not swallowed | **physics** | `personas-web` invented a *better* answer than ours — a `parseError` taint flag carried into localized UI (`reviewStore.ts:35-39`), so the human sees the degradation instead of a log nobody reads |
| Exactly two policies, chosen by "lie to the user vs lost job" | **ergonomics** | the *rule* is portable; a two-item menu is calibrated to a repo with 793 sites |
| `collect_rows(rows, context)` as a **factored helper** | **house convention** | zero siblings factored it. But three reinvented the *policy* unfactored — `vibeman` writes the exact trilemma out longhand at `repository.utils.ts:251-255`, `ascent` copy-pastes the skip idiom **13×** in one directory. Unique packaging, corroborated substance |
| The per-field tolerance idiom is banned outright | **house convention** | see §8 Gap 4 — it is a workaround for a missing migration ledger. `personas-cloud` has the *same* idiom for the *same* reason (`db.ts:466-474` overrides pairing with its `ADD COLUMN … DEFAULT` migrations), which suggests the ban is only correct once the upstream gap is closed |

Where a clause is marked **house convention** it must not be exported as doctrine. `personas-web` and `personas-cloud` are different stacks with no row cursor, so their *silence* on a clause is weak evidence; `brainiac` (Rust, same problem shape) is the strong oracle and its agreements and disagreements are both load-bearing.

## 3 Mandated primitives

**Exist today — use them:**

- **`db/src/repos/utils.rs:33` — `collect_rows<T>(rows, context) -> Vec<T>`.** The only skip-and-log primitive in the tree. Logs `context`, `row_index` and the error per failure, then a summary `skipped_count` line, then returns the survivors. **107 call sites.** It is correct as written; the problem is exclusively *where* it is and is not used.
- **`db/src/macros.rs:100` — `row_mapper!(row_to_x -> Model { … })`.** Generates a name-addressed mapper from a field list. `[bool]` for `INTEGER`-stored booleans. **44 invocations across 34 files.** Prefer it over a hand-written mapper whenever the struct is a flat 1:1 of the row — it cannot be written positionally, which is its main virtue. **Do not use its `[opt]` / `[opt_str]` / `[opt_i32]` kinds** (§5).
- **`db/src/macros.rs:141` — `crud_get_by_id!`**, **`:179` — `crud_get_all!`**, **`:376` — `lab_crud!`**. Generated repo functions. `crud_get_all!` routes through `collect_rows`; `lab_crud!`'s two list functions propagate. **These two disagree and neither says why** (§7).
- **`db/src/macros.rs:331` — `timed_query!("<table>", "<table>::<op>", { … })`.** Wraps the repo function body. Its second argument is the string you should reuse verbatim as `collect_rows`' `context`, so a slow-query warning and a skipped-row warning name the same operation.
- **`rusqlite::OptionalExtension::optional()`** — **43 sites in repos.** The correct single-row "absent is not an error" spelling. Use it instead of matching `QueryReturnedNoRows` by hand.
- **`impl FromSql for <Enum>`** — **6 impls** (`core/src/models/automation.rs:64,119,180`, `chat.rs:47`, `n8n_session.rs:45`, `core/src/lifecycle.rs:340`). Each maps an unknown stored token to `FromSqlError::Other`, so the row fails and the call-site policy applies. **This is the right *location* for enum handling — a `FromSql` impl is the only place a stored token can be interpreted once — but not, as written, the right *policy*** (§5).
- **`db/src/repos/core/personas.rs:339-346` — `ProfileMode` + `row_to_persona_with_mode`.** One mapper, an explicit `Decrypt` / `Redact` parameter, and two thin wrappers (`row_to_persona` `:435`, `row_to_persona_redacted` `:439`). **The model for any cross-cutting row-level policy** — secret redaction is decided once, in the mapper, so a list endpoint physically cannot leak a token by forgetting.
- **`db/src/chain.rs:156-203` — `CostCeilingReading { Disabled, Configured(f64), Corrupt(String) }`.** The repo's own three-state read result, with the reason written down at `:154-155`: *"Unset and corrupt are deliberately NOT the same variant."* This is the shape §8 Gap 2 asks for at the row-set level, already invented one layer down.
- **`core/src/crypto.rs:1394-1418` (and `:1564`, `:1781`) — the partial-result pattern, already built.** The credential-migration reads collect survivors, `error!` each failure with its row index, `warn!` a summary, and **return `(rows, parse_failures)` to the caller**, which threads the count out through the command's return value (`:1454`, `:1608`, `:1860`). That is `collect_rows_partial` below, hand-rolled three times in the wrong crate under no name. **Extract it rather than reinventing it.**

**Do not exist — this path defines them:**

- **`db/src/repos/utils.rs` — `collect_rows_strict<T>(rows, context) -> Result<Vec<T>, AppError>`** and **`collect_rows_partial<T>(rows, context) -> (Vec<T>, usize)`.** The first is the propagating policy given a *name*, so the choice becomes visible at every call site instead of being an anonymous turbofish (Gap 3). The second is the extraction of the `crypto.rs` shape above (Gap 2) — it already has three proven users on day one.

## 4 Steps

1. **Find the existing mapper before writing one.** `grep -n "fn row_to_" <repo module>`. There are 169 named mappers and the correct number per struct is one; `row_to_execution` (`executions.rs:77`) already maps every `persona_executions` column and is reused by 6 functions.
2. **Write the mapper as `fn row_to_<entity>(row: &Row) -> rusqlite::Result<Entity>`**, private, at the top of the repo module under a `// Row Mappers` banner (`communication/messages.rs:10-14` is the shape). If the struct is a flat mirror of the table, use `row_mapper!` instead and stop here.
3. **Address every column by name.** `row.get("persona_id")?`. Never `row.get(0)`. If you are tempted by position because the query is a hand-written column list, name the columns anyway — `SELECT` aliases are addressable by name too (`executions.rs:1955` reads `row.get("completed")` off an aggregate).
4. **Let every field propagate with `?`.** No `unwrap_or`, no `.ok()`, no default. A `bool` stored as `INTEGER` is `row.get::<_, i32>("enabled")? != 0`; a genuinely nullable column is `Option<T>` in the struct and `row.get("col")?` still.
5. **Choose the set policy at the call site, out loud.**
   ```rust
   // user-facing list — a short list is a lie
   let rows = stmt.query_map(params![persona_id], row_to_execution)?;
   rows.collect::<Result<Vec<_>, _>>().map_err(AppError::Database)
   ```
   ```rust
   // background sweep — a dropped row is a job nobody will run
   let candidates = collect_rows(
       stmt.query_map([], row_to_candidate)?,
       "persona_executions::sweep_zombie_executions",
   );
   ```
   Write the one-line reason above the `collect_rows` call, as `executions.rs:1720-1723` does. That comment is currently the only written statement of this rule anywhere in the repo.
6. **Reuse `timed_query!`'s operation string as the `collect_rows` context** so both log lines name the same thing. 26 of the 99 existing contexts are bare function names (`"get_recent"`, `"claim_pending"`) that don't say which table — don't add a 27th.
7. **For an enum column, `impl FromSql`** on the enum in `core/src/models/` — one interpretation site, not a `from_db(&str)` helper every caller may or may not use. Inside it, map an unknown stored token to the **least-privileged, least-terminal** variant and `tracing::warn!` the raw value; do not fail the row and do not pick the convenient variant. ("Least-terminal" = the state that keeps the record actionable — `pending`, not `rejected`; `open`, not `closed`; `running`, not `failed`.)
8. **Write the test against a real chain.** `init_test_db()` (`db/src/lib.rs:1882`), insert, read back, assert. If your mapper carries a `Json<T>` column, **also** insert a row with a deliberately malformed blob and assert what your call site does with it — that test does not exist anywhere in the tree today (§8 Gap 6), and it is the only thing that distinguishes your intent from an accident.
9. **Stop.** No second mapper, no `impl From<&Row>`, no mapping in the command layer.

## 5 Anti-patterns

- **`rows.filter_map(|r| r.ok()).collect()` — 111 sites.** The single largest defect generator here. It deletes the row *and* the evidence: no log, no count, no error, and the caller receives `Ok`. `db/src/repos/resources/db_schema.rs:23` returns a user's database-schema table list this way; `db/src/migrations/helpers.rs:51` re-encrypts credentials this way, so a credential whose row fails to map is silently left un-migrated forever.
- **`rows.flatten().collect()` — 62 sites.** Identical semantics, harder to see: `Iterator::flatten` over `Result` discards `Err`. `core/memory_claims.rs:163` is `Ok(rows.flatten().collect())` — one line, and nothing in it says "some claims may be missing".
- **Wrapping the whole read in a closure and `.unwrap_or_default()` — 6 sites.** Drops the *entire* result set on any failure, including a failure to `prepare`. `src/commands/design/n8n_transform/confirmation.rs:204-212` loads existing tool definitions this way to deduplicate against; an empty list means the dedup finds nothing and the confirmation step **creates duplicate tool definitions**. Same shape at `:430-442` for connectors. `src/commands/credentials/vector_kb.rs:1418,1462` do it in the orphan-cleanup path — fail-safe by luck, not by decision, and the *sibling* `.unwrap_or(true)` four lines below at `:1441` carries the explanatory comment the row-set one doesn't.
- **Per-field tolerance: `row.get("col").unwrap_or(None)` — 94 sites — and its macro spellings `[opt]` (24), `[opt_i32]` (3), `[opt_str]` (1).** These convert `InvalidColumnName` — "your query does not select this column" — into a plausible `None`, and there is a **live, shipped instance**: `communication/messages.rs:28` reads `use_case_id` tolerantly, `get_thread_summaries` (`:284-288`) enumerates `pm.id … pm.thread_id` and never selects `pm.use_case_id`, so **every thread in the inbox reports `useCaseId: null` regardless of what is stored.** The idiom is what makes that invisible.
- **A tolerant default that fails *open*.** `system_ops.rs:22` — `enabled: row.get::<_, i64>("enabled").unwrap_or(1) != 0`. An automation whose enable flag cannot be read **runs**. Two lines later `:28-31` defaults a missing `unattended_mode` to `"auto"`, i.e. runs without approval. Both are kill-switches defaulting to off-the-brakes.
- **A domain default baked into a generic macro.** `macros.rs:120-123` — `[opt_str]` hardcodes `unwrap_or_else(|_| "working".to_string())`. Any struct in any repo that uses `[opt_str]` inherits the string `"working"` for a column that could not be read. It has exactly one user (`core/memories.rs:125`, a `tier` field), which is one more than a macro this shape should have.
- **Enum columns: the repo has two strategies and neither is the convergent one.** *(This entry was rewritten after the sibling sweep — the first draft said "always `impl FromSql`, which fails the row", and four independent codebases disagree.)* Six enums `impl FromSql` and map an unknown token to `FromSqlError::Other`, which **fails the row** and — under the 475 propagating call sites — fails the whole read: one legacy status token from a rolled-back migration can empty a list. Four others use `from_db(&str) -> Self` with a catch-all and **silently invent** a variant: `lab.rs:31` → `Failed`, `evolution_status.rs:41` → `Failed`, `review.rs:25` → `Pending`, `automation_suggestion.rs:72` → `Rejected`. No log in any of the four, and two pick the *dangerous* direction — an unreadable suggestion becomes `Rejected` (silently discarded) and an unreadable run becomes `Failed` (terminal, never retried). Only `review.rs`'s `Pending` matches the convergent rule by accident. **The answer four sibling repos reached independently is neither: degrade to the least-privileged / least-terminal variant *and log the raw token*.** `brainiac` `documents.rs:648` (`RevisionPolicy::parse(…).unwrap_or(NeedsReview)`), `personas-web` `supabaseApi.ts:73-82` (unknown execution status → `"running"` + a `console.warn` with a comment explaining that a blind cast would poison success-rate math and `eq("status", …)` filters), `ascent` `improvement.ts:147` (unknown PR state → `"open"`) and `members.test.ts:543` (corrupt role → `"member"`, *pinned by a test*).
- **Making the mapper infallible so the failure "can't happen".** It does not remove the failure, it relocates it somewhere worse. `brainiac`'s 8 infallible `row_to_*` functions use sqlx's panicking `r.get()`, so a type mismatch takes down the request thread rather than one row; `personas-cloud`'s `mapRow` ends in `return result as T` (`db.ts:462`), so a missing column silently produces `undefined` on a required field and the malformed object flows into business logic. A mapper returning `Result` is the cheap version of this problem.
- **Positional `row.get(0)` against an explicit column list.** 56 of the 85 inline mapping closures in `db/src/repos` and **48 of the 52 in `src/`** are positional. The failure is not the column *count* changing (SQLite appends), it is a column being **inserted mid-list** during an edit: every subsequent index shifts, and because most columns are `TEXT` the mapper keeps parsing and produces a struct with fields swapped. Nothing fails. `research_lab.rs:124-149` shows the only defensible form of this — a `SOURCE_COLUMNS` const with a doc comment stating *"The SELECT column order must match"* — and even that is a comment, not a check.
- **Mapping rows outside the repository layer.** **262 of the 793 `query_map` sites are in `src/` and `engine/`** — command handlers, the companion brain, the MCP server — where the repo's conventions do not reach. `collect_rows` is used **once** in all of them (`engine/src/event_vocabulary.rs:244`). In `src/` the silent-skip rate is **48%** against **10%** inside `db/src/repos`. Whatever discipline exists lives in the repo layer and does not survive leaving it. See §7's second-pass finding for why.
- **A mapper that decides.** Any `warn!`, `unwrap_or`, or fallback inside `fn row_to_*` moves a policy decision to a place with no context about who is asking. The mapper's whole job is to convert or fail.
- **A second mapper for the same struct.** `row_to_persona` / `row_to_persona_redacted` / `row_to_persona_lean` looks like three but is one plus two wrappers and one deliberate projection — that is fine. Two independent full mappers for one struct is not; they drift.

## 6 Evidence

**Adoption:** 793 `query_map` sites · 169 named mappers (125 hand-written `fn row_to_*` — 110 in `db/src`, 15 in `src/` — plus 44 `row_mapper!` invocations across 34 files) · 137 inline struct closures · 107 `collect_rows` calls · 43 `optional()` calls · 381 `SELECT *` statements.

- **`db/src/repos/execution/executions.rs:1717-1736` — copy this one.** The only site in the tree that states the rule and then follows it:
  ```rust
  // A row that fails to map here is a zombie candidate that would
  // never be reaped — log it (collect_rows) instead of dropping it
  // silently.
  ```
  A comment naming the consequence, then `collect_rows` with a `table::op` context. Every other `collect_rows` call is unexplained.
- **`db/src/repos/utils.rs:33-58`** — `collect_rows` itself. 25 lines. Logs `context` + `row_index` + `error` per skip, then a summary count. Correct; under-adopted.
- **`db/src/repos/core/personas.rs:339-346, 435-449`** — `ProfileMode` + `row_to_persona_with_mode`. The mapper as the choke point for a cross-cutting row policy (token redaction). Copy this shape whenever "this field is different depending on who's reading".
- **`db/src/chain.rs:154-203`** — `CostCeilingReading`. Three states, `Corrupt(String)` carrying the raw value for the audit trail, and a doc comment explaining why corrupt ≠ unset. **The repo already knows the answer; it just hasn't applied it one layer up.**
- **`db/src/byom.rs:243-257`** — refuses to fall back to open access on a corrupt policy blob, with the reason logged. The same instinct, in the security direction.
- **`core/src/crypto.rs:1394-1418`** — the best row-set handling in the tree, and nobody knows it exists. Skips the unreadable row, `error!`s it *with its index*, `warn!`s a summary that names the consequence (*"row(s) could not be read and remain unencrypted"*), and returns the failure count to the caller instead of hiding it. This is what §8 Gap 2 asks for, already written, three times, inline.
- **`db/src/macros.rs:100-128`** — `row_mapper!`. Its `@get` arms make name-addressing the only spelling available; that is why its 44 invocations have a 0% positional rate.
- **`db/src/repos/communication/messages.rs:10-33`** — the module layout to copy: a `// Row Mappers` banner, every mapper together at the top, one per struct. (Its `use_case_id` line is the deviation in §7; the *layout* is right.)
- **`core/src/models/automation.rs:64-70`** — the right *shape* for an enum column: four lines, one interpretation site, `impl FromSql`. Copy the shape, then apply §5's policy inside it (degrade + log) rather than its current `FromSqlError::Other`.

### Convergence — what five sibling repos did without reading this

Run 2026-08-14, read-only, against `brainiac` (Rust · sqlx · Postgres — the strong oracle, same problem shape), `personas-cloud` (TS · better-sqlite3), `personas-web` (TS · Supabase), `vibeman` (TS · better-sqlite3), `ascent` (TS · Prisma).

- **The `row_to_*` name is real doctrine.** Reinvented verbatim in three repos across two languages. Assert it; don't argue for it.
- **Name-addressing is real doctrine, and Personas is the outlier.** `brainiac` has **601 name-addressed column reads and zero positional ones** in its entire tree. The three TS repos cannot address positionally at all. No sibling pays the cost Personas pays at 104 of its 137 inline mapping closures. Whatever the original reason was, it is not a cost other people accept.
- **`brainiac` independently invented the column-contract const** (`DOC_COLUMNS`, `MEMORY_COLUMNS`, `SCHEDULE_COLS`) that `research_lab.rs:149` calls `SOURCE_COLUMNS` — but pairs it with **name** access, where Personas pairs it with **position**. The const is convergent; the positional coupling is ours alone and is the part that can silently swap two fields.
- **`brainiac` has the skip-and-log doctrine and never applied it to SQL.** `contradict.rs:217` (`// unparseable verdict: skip, never guess`) and `okf_ingest.rs:268` (`warn!(… "unreadable, skipped")`) prove the instinct, while its store layer at `documents.rs:699,729` collects revisions into a `Result` where **one bad row fails the entire list** — the exact defect this path names, unfixed, in the sibling closest to us. Two repos, same blind spot, independently.
- **`vibeman` wrote our rationale out longhand for a different layer.** `repository.utils.ts:251-255` names all three options — *"a raw `JSON.parse` (crashes the read)"*, *"a silent `{}` fallback (corruption-on-read)"*, or *"non-throwing… with logging on malformed input"* — and picks the third. That is the `collect_rows` trilemma, solved for JSON fields and never lifted to rows.
- **`personas-web` beat us on the same idea.** `reviewStore.ts:35-39` keeps a corrupt row, tags it `parseError: true`, **escalates it to `critical` rather than the convenient `info`** (with the reason written down: `info` would silently widen the SLA and route it to auto-approve), and renders the taint in three components with translations in every locale. Degradation surfaced to the human, not to a log. That is what §8 Gap 2 should be built toward.
- **`ascent` is the only repo in the survey that tests any of this**, and it is not close: 11 test files in `src/lib/db` with the invariant named in the test title. `playbooks.test.ts:428` — *"returns [] for malformed stored JSON instead of throwing (one bad row can't 500 the route)"*. `scans-read.test.ts:16-18` — *"every helper is TOTAL… a single corrupt scan row can never crash or NaN-render the shareable report page"*, with literal corrupt fixtures (`"{ not json"`, `"}{ corrupt"`, `"[1, 2, "`). `integrations.test.ts:97`, `org-signals.test.ts:124,220,409,498`, `members.test.ts:543`, `plan.test.ts:719`, `org-gate.test.ts:78`. **Personas, brainiac, personas-cloud and vibeman have zero.** Steal this pattern (§8 Gap 6) — it is the cheapest item in this document and the only one that turns the policy from an assertion into a fact.
- **What nobody reinvented:** `collect_rows` as a *factored, shared helper*. Zero of five have an equivalent. Since three of five reinvented the policy in unfactored form, the honest reading is that the packaging is ours and the substance is not — hence its **house convention** tag in §2.

## 7 Deviations found

### The distribution — six policies for one situation

Measured over all 793 `query_map` call sites. The spine records this leaf's convergence as `diverged`; this is what that means numerically.

| Policy | Sites | % | What the user sees when one row fails |
|---|---:|---:|---|
| **Propagate** — `collect::<Result<Vec\|HashMap\|HashSet>>` · manual loop with `?` | **475** | 59.9% | an error; the whole read fails |
| **Skip + log** — `collect_rows` | **107** | 13.5% | a short list; a `warn` names the row index and the error |
| **Skip + log, hand-rolled** — a `match` / `filter_map` with a `warn!`/`error!` in the `Err` arm. **Four distinct re-implementations of `collect_rows`**: `execution/metrics.rs:790-796` · `execution/knowledge.rs:345-352` · `core/src/crypto.rs:1394-1418` (3 sites, and the best version — it returns the failure count) · `communication/sla.rs:168-204` `batch_query_map` (private wrapper, 4 sites) | **15** | 1.9% | same behaviour, five spellings |
| **Skip, silent** — `filter_map(\|r\| r.ok())` · `.flatten()` · `if let Ok` | **173** | 21.8% | a short list; nothing anywhere records it |
| **Whole set dropped, silent** — closure + `.unwrap_or_default()` | **6** | 0.8% | an empty list, reported as success |
| Single-row `.next()` (not a set) | 8 | 1.0% | — |
| Unresolved by the classifier (9 sites, listed in the scan output; `sla.rs:437` was read by hand and is propagating) | 9 | 1.1% | — |

Seven per-file mappers are reached by call sites that disagree about the failure policy. ### Structural — and the thing that is upstream of most of the rest

**The repository boundary is advisory, and that single fact explains the layer split above.** `106 of 564` files under `src-tauri/src/` prepare SQL directly — **42 in `companion/`, 36 in `commands/`, 24 in `engine/`** — holding a `DbPool`, writing their own statement, and mapping their own rows. Nothing stops them: `collect_rows` is `pub` (`utils.rs:33`) and `pub mod utils` is re-exported (`repos/mod.rs:19`), so the primitive is one `use` away from every one of those files, and it is imported by **zero** of them.

Re-read against that, the deviations are not 793 independent bad choices. They are **two populations**:

| | inside `db/src/repos/**` | outside it (`src/**`) |
|---|---|---|
| named mapper convention | 110 mappers, 90% name-addressed | 15 mappers, **80% positional** |
| inline closures | 85, 66% positional | 52, **92% positional** |
| `collect_rows` | 105 uses | **0** |
| silent skip rate | 10% | **48%** |

Inside the layer there is a real, if unwritten and unevenly applied, convention. Outside it there is none at all — and *outside is 33% of the sites*. Every downstream item in this section is a symptom of that: the policy divergence, the positional mapping, the missing logs. **Any fix that only edits `db/src/repos/**` addresses two-thirds of the problem and leaves the two-thirds-worse third untouched.** The census rule in §9 is deliberately rooted at `src-tauri`, not `src-tauri/db`, for exactly this reason.

### Structural — the rest

- **`collect_rows` has been re-implemented four more times.** `execution/metrics.rs:790-796` and `execution/knowledge.rs:345-352` inline the `filter_map` + `warn!` shape; `core/src/crypto.rs:1394-1418` writes a better one (with a returned failure count) three times; `communication/sla.rs:168-204` `batch_query_map` / `:207` `batch_query_map_vec` wrap the loop privately for 4 call sites. Five spellings of one 25-line function is what "the primitive is not discoverable" looks like from the inside.
- **The two shipped CRUD macros contradict each other.** `crud_get_all!` (`macros.rs:179-195`) generates a list function that routes through `collect_rows`, and its own doc comment at `:171` says *"using `collect_rows` for resilience."* `lab_crud!`'s `get_runs_by_persona` (`:419-422`) and `get_results_by_run` (`:552-555`) propagate. Both macros live in the same file, ~230 lines apart, with no comment acknowledging the difference. **5 tables get resilient lists and 5 get fail-fast lists purely by which macro their module adopted.**
- **The rule is stated in exactly one place and it is a code comment.** `executions.rs:1720-1723`. Not in `CLAUDE.md`, not in `.claude/conventions.json` (which contains no `row_to`, `collect_rows`, `row_mapper` or `query_map` entry), not in `db/src/repos/mod.rs` (23 lines of `pub mod`, no module doc).
- **`collect_rows`' own log context is inconsistent.** 73 of 99 context strings are `module::op`; 26 are bare (`"get_recent"`, `"get_pending"` ×2, `"claim_pending"`, `"skipped_rate_by_type"`, …). A `warn` reading `context=get_recent` cannot be traced to a table.
- **Positional access dominates outside the named mappers.** Named `fn row_to_*`: 99 of the 110 in `db/src` are name-addressed (90%), and all 44 `row_mapper!` invocations are name-addressed by construction — the convention is real. But **12 of 15 named mappers in `src/` are positional (80%)**, and of the 137 inline closures, **104 are positional** (56/85 in repos, 48/52 in `src/`). The convention's boundary is `db/src/repos` + `fn row_to_*`, and nothing enforces the boundary. For scale: the nearest sibling repo (`brainiac`, Rust, same problem shape) has **601 name-addressed reads and zero positional ones**, so this is not a cost the ecosystem accepts — it is local.
- **381 of ~557 prepared statements in `db/src/repos` are `SELECT *`.** That is the *safe* pairing with name addressing and it is why the positional mappers have not broken yet — but nine table rebuilds exist (`fk_hygiene.rs:117`, `incremental.rs:104`) and a rebuild is exactly the event that reorders columns. See [schema-change](./schema-change.md).
- **`collect_rows` has no test.** `db/src` contains 770 `#[test]` functions and `db/src/repos/utils.rs` has no `mod tests` at all. Nothing anywhere asserts that a corrupt row is skipped rather than dropped, or that the skip is logged. This is the same finding as [json-blob-column](./json-blob-column.md) Gap 8, reached from the other side.
- **Two enum strategies, neither convergent — and the split is 6 vs 4 with no rule.** See §5. The relevant structural fact is that an enum's failure policy is decided in `core/src/models/`, three layers away from the call site that will live with it, and the two spellings (`impl FromSql` vs `fn from_db`) are indistinguishable at the mapper.

## 8 Gaps in the primitive

1. **`Json<T>` turns a one-field corruption into a whole-row disappearance, and this path is where it lands.** `Json<T>`'s `FromSql` (`core/src/models/json_column.rs:91-98`) returns `FromSqlError::Other`; the `?` in the mapper propagates it as a *row* error; `collect_rows` then drops the row. So a corrupt `tool_steps` blob does not degrade one field — it deletes an execution from the list, with a `200`. The full analysis, the `try_from_sql_lossy` proposal and the 22-field adoption census live in [json-blob-column](./json-blob-column.md) §Gaps 1 and are not repeated here. **What belongs to *this* path is the consequence:** the blast radius of a JSON decode is set by the collection policy, and 475 sites choose "fail the read" while 107 choose "delete the row" and neither was chosen with `Json<T>` in mind.
2. **There is no partial-result type — but there are three hand-rolled instances of one.** A repo function returns `Result<Vec<T>, AppError>`, which can say "everything" or "nothing" and cannot say "89 of 92". So a caller that would happily render 89 rows with a warning banner has no way to learn there were 92. `db/src/chain.rs:156` proves the repo can model this for a *single setting*; **`core/src/crypto.rs:1394-1418`, `:1564`, `:1781` prove it can model it for a set** — they return `(rows, parse_failures)` and thread the count out to the command. Three proven users, no shared type, no name, in the crypto crate. **And `personas-web` built the client half.** `reviewStore.ts:35-39` keeps the degraded row, tags it `parseError: true`, and carries the taint into three UI components with translations in every locale, so the human sees "this row is partly unreadable" instead of the operator maybe reading a log. `collect_rows_partial` (§3) is the ~10-line Rust half; the taint flag reaching the binding and the surface is the other half, and it is the one that matters.
3. **The propagating policy has no name.** `collect_rows(rows, ctx)` is a named, greppable, documented decision. Its opposite is `rows.collect::<Result<Vec<_>, _>>().map_err(AppError::Database)` — a turbofish that reads as plumbing. **That asymmetry is the whole reason the policies diverged:** one branch of the choice is a word you can search for and the other is punctuation. This is the same shape as `json-blob-column` Gap 6 (`unwrap_or_default()` is shorter than the correct fallback) and it has the same fix: give the right answer a name.
4. **The per-field tolerance idiom exists for a real reason.** `.unwrap_or(None)` is not laziness — it is a workaround for a repo with no applied-migrations ledger (see [schema-change](./schema-change.md) Gap 2), where a mapper may genuinely run against a schema that has not caught up. Banning it without fixing that leaves a real failure uncovered. The honest fix is upstream: with a migration ledger, a column either exists or the boot failed, and every one of these 122 sites becomes a plain `?`.
5. **`rusqlite` cannot tell "no such column" from "wrong type" at the type level.** Both arrive as `rusqlite::Error`, so `.unwrap_or(None)` cannot be narrowed to only tolerate the schema-lag case even by an author who wants to. A `get_if_present(name)` helper that matches only `InvalidColumnName` and propagates everything else would let step 4's ban be total; it does not exist.
6. **No test in the tree feeds a malformed row to a mapper.** 770 `#[test]`s in `db/src`, and the entire policy taxonomy above — 6 policies, 793 sites — is unverified behaviour. `collect_rows` could be changed to drop *every* row and every test would pass. **The pattern to copy is `ascent`'s** (§6): put the invariant in the test *name* so the intent survives a refactor — `it("returns [] for malformed stored JSON instead of throwing (one bad row can't 500 the route)")` — and feed literal garbage fixtures (`"{ not json"`, `"}{ corrupt"`, `"[1, 2, "`) rather than well-formed-but-wrong values. Three tests would close this: a corrupt `Json<T>` blob under a `collect_rows` caller (assert the row is skipped **and** a warn fired), the same blob under a propagating caller (assert `Err`), and an unknown enum token (assert the least-terminal variant + a warn). All three fit inside one `#[cfg(test)]` module in `db/src/repos/utils.rs`, which currently has none.
7. **Nothing checks that a mapper's column names are in its query's `SELECT`.** This is the root cause of the `use_case_id` P0 and it is genuinely hard: the mapper and the SQL are in different functions, the SQL is often `format!`-assembled, and the join is at runtime. `SELECT *` hides it (381 sites) and an explicit column list exposes it (~176). See §9 for why this is the one signal that cannot be a census rule.
8. **Nothing makes the repository layer a boundary.** `DbPool` is `Clone` and reachable from any command handler; `conn.prepare` is free. There is no `pub(crate)`, no module wall, no lint. The 106 SQL-writing files under `src/` are not rule-breakers — they were never told there was a rule, and Rust's visibility system was never used to say so. A real fix is architectural (move the reads into `personas-db`, or gate the pool behind a repo-only accessor), which is out of scope for this path; what belongs here is that **the convention cannot be enforced by documentation while the boundary is unenforced by the compiler**, and 48% silent-skip on the far side is the measurement of that.
9. **No enforcement reaches `src-tauri/` for any of this.** `npm run check` is TypeScript + ESLint over `src/`; lefthook is eslint + secrets + i18n. `cargo clippy -D warnings` runs in CI and has no opinion about which iterator adapter you use on a `MappedRows`. Every deviation above shipped green.

## 9 The missing gate

### The semantic condition, stated first

> **A read of a row *set* discards a per-row mapping failure without recording it.**

That is the condition. It is stack-free: any language with a fallible row cursor can express it, and any repo can decide what "recording it" means. What follows is **one repo's proxy for it**, and per the [portability test](../research/portability-test.md) the proxy does **not** travel — an adopting repo must re-derive its own against its own idiom (SQLAlchemy's `.scalars()`, a `try/catch` inside a `.map()`, `serde` on a row batch, …). What travels is the sentence above and the intent.

### The proxy, and what it keys on

In this tree the condition is worn by exactly three spellings applied to a `query_map` result: `filter_map(|r| r.ok())`, `filter_map(Result::ok)`, and `.flatten()`. All three are *generic* Rust idioms — which is precisely why the signal must be **anchored to `query_map`** rather than matched on its own. Unanchored, `.flatten()` alone matches hundreds of `Option` chains and the rule becomes noise.

**Precondition the proxy depends on, stated so it can be checked before porting:** this repo reduces row iterators with iterator adapters written within ~700 characters of the `query_map(` call, and does not wrap them in helper functions. Measured: **148 matches across 64 files**, of which **144 are production and 4 sit inside `#[cfg(test)]` modules** (2.7% noise, in `dev_tools.rs`, `src/bench/db.rs`, `src/engine/mod.rs` — not excluded, because excluding those three production files wholesale would hide real violations). Eight sampled matches were opened and read: **8/8 true positives.** Recall against the hand-classified corpus is **148 of 173** (86%); the misses are two-statement forms with intervening statements, and they are misses, not false negatives that matter — a ratchet does not need perfect recall, it needs to be unable to rise.

### Mechanism — a census rule, not a script

Per the [contract](../golden-path-contract.md) §"Don't write a script", the ratcheting-baseline mechanism already exists at [`scripts/census/`](../../../scripts/census/). This path adds **one entry** to `scripts/census/rules.json`:

```jsonc
{
  "id": "silent-row-skip",
  "goldenPath": "docs/concepts/golden-paths/row-to-struct-mapping.md",
  "title": "Row-set read that discards per-row mapping failures without logging",
  "roots": ["src-tauri"],
  "extensions": [".rs"],
  "signal": {
    "pattern": "query_map\\((?:[^;]|\\n){0,700}?(?:SKIP|\\?;[^;]{0,200}SKIP)",  // SKIP = the three spellings
    "flags": "g",
    "ignoreCommentLines": true,
    "description": "…"
  },
  "baseline": { "files": 64, "matches": 148 },
  "floor": 900
}
```

Landed and verified: `node scripts/census/run-census.mjs --check` reports `OK  silent-row-skip  64/64 files  148/148 matches  963 walked  floor 900`, alongside the six sibling rules (7 rules, 22,687 file-visits), and `census:test` stays at 21/21.

The runner supplies the whole §9 fail-loud requirement so this path does not re-derive it: it **fails** (not warns) when the walk sees fewer than `floor` files, when the rule matches zero files anywhere, when a count rises, and — the one that matters most for a Rust root — **when a count drops without the baseline being updated**, because a silent drop after a refactor is a broken matcher far more often than it is fixed code. Surviving counts print on success.

**Floor rationale.** The walk sees **963 `.rs` files**, which is exactly `rust.files` in [`shared-facts.json`](../shared-facts.json) — the census engine's `ALWAYS_SKIP_DIRS` already excludes `target/`, so two independently-derived counts agree, which is the only reason to trust either. `floor: 900` leaves room for normal file churn while making a moved crate or a renamed root fail loudly instead of reporting a clean tree. It is set to **match `deferred-read-then-write`**, the other `src-tauri`-rooted rule, deliberately: two rules over the same root must not hold two different opinions about what "the Rust tree is intact" means, or the weaker one keeps passing while the stronger fires and a reader has to work out which to believe.

**No `exclude` entries.** Deliberate: every candidate exemption here (the four test-module matches) would require excluding a whole production file, and a stale exemption is how an allowlist becomes the bug. The 4 test hits are carried in the baseline and named above so the next reader knows the number is 144 + 4, not 148.

### Two more census rules — the schema-ordinal pair

`silent-row-skip` above is about what happens when a mapping **fails**. This pair
is about a mapping that **succeeds and is wrong**, which is the worse outcome
because nothing anywhere reports it. Gap 7 already names the mechanism: *"Nothing
checks that a mapper's column names are in its query's `SELECT`. … `SELECT *`
hides it (381 sites) and an explicit column list exposes it."* The join between
mapper and SQL is not expressible as a regex — §9 below says so and that stands —
but **each of the two halves separately is**, and each is a ratchet the other
cannot substitute for.

> **The condition, stack-free:** *a persistence read is bound to the ORDER of a
> schema rather than to its NAMES, and the projection that fixes that order is
> not written down at the call site.*

The two halves compound, and that is why they ship together rather than as one
rule. `SELECT *` fixes the ordinal mapping to `CREATE TABLE` order; a positional
`row.get(N)` consumes that mapping; and `db/src/migrations/incremental.rs` adds
columns as a matter of routine. So an additive migration — legal, reviewed,
touching no query file — can shift every read below the insertion point, and it
will usually still type-check, because column 7 and column 8 are both `TEXT`.
Fixing one half alone does not close it: a named read against a wildcard
projection still over-fetches every BLOB on the table, and a named projection
consumed positionally is still ordinal.

**The compliant shape is present at scale on both halves, which is what makes
these ratchets rather than rewrite proposals.** Named-column reads score
**1,440 matches across 51 files** against the 1,479 positional ones — this repo
is almost exactly half migrated. Named projections score **391 matches across 83
files** against 379 wildcards. Neither half is a minority practice being
legislated into existence; both are the majority-or-parity practice, unenforced.

**Precision, hand-measured.** `positional-row-get`: **12/12** on a systematic
sample opened by hand (every 123rd site), all real rusqlite positional reads
inside a `query_map`/`query_row` closure — `cdc.rs:479`, `repos/lab/versions.rs:100`,
`repos/resources/broker_edges.rs:113` in its turbofish spelling, and so on. The
receiver vocabulary was enumerated exhaustively rather than sampled: exactly two
identifiers carry a positional get in this tree, `row` and `r`, which is the
anchor that keeps `args.get(0)` and `map.get(k)` — a different concept wearing
the same method name — out of the count. `select-star-in-repo`: **12/12** on a
systematic sample, all real wildcard projections; the mandatory whitespace is the
discriminator that keeps `SELECT COUNT(*)` out, and 110 aggregate counts in the
same tree match zero times.

**Declared false-positive surface, because it is real and small.** **22 of the

`conn.query_row("SELECT COUNT(*) …", [], |r| r.get(0))` — where there is no
column name to read by and `get(0)` is the only spelling available. They are

stale exemption is how an allowlist becomes the bug. The honest number is 1,457

### What this rule does NOT cover, and why the second half needs ESLint's *shape*, not ESLint

Two conditions from §7 are real and are **not** countable:

1. **A mapper column name that the query does not `SELECT`** — the `use_case_id` P0. This needs the mapper's field list joined to the SQL string that feeds it, across functions, through `format!` assembly. That is AST + dataflow, not a regex. **It cannot be an ESLint rule either** — ESLint does not see Rust. The right host is a **Rust test in `personas-db`**: run the real chain, execute each repo list function against a seeded row, and assert every field the mapper reads is non-defaulted. That inverts the problem from "parse the SQL" to "observe the behaviour", which is the only version that can work, and it satisfies the model-effort guide's warning that *a gate that asserts data is not a gate on behaviour*. **It must run under `cargo test --workspace`** — [schema-change](./schema-change.md) Gap 9 and [json-blob-column](./json-blob-column.md)'s corrections note both record that `personas-db` tests were dark until `--workspace` landed; a test placed there without that flag would be written, merged, and never executed. **Verified 2026-08-14: `ci.yml:275` is now `cargo test --workspace --manifest-path src-tauri/Cargo.toml --features desktop`, with the reason in a comment at `:269`, so the lane is live in CI.** It is still NOT live locally — `npm run test:rust` passes `--lib` against the root manifest; use `cargo test -p personas-db` or `npm run test:rust:crates`.
2. **Divergent policy at the call sites of one mapper** (§7's three cases). This is a *relational* property — "the set of policies applied to mapper X has cardinality > 1" — and a census rule counts occurrences, not relations. It is a good candidate for the same Rust test lane, computed from the same parse.

Both are named here rather than hand-waved: the census rule ratchets the 148 silent skips down and cannot rise; the two structural conditions need the behavioural test lane, and that lane's precondition is `--workspace`, which is checkable in one line before anything is built on it.
