# Moonshots — Security & Credentials

## 1. The Zero-Plaintext Credential Broker — Personas as the machine's identity fabric
- **Tier**: 1 (10x category-defining)
- **Category**: trust
- **Impact**: Every agent, script, Claude Code session, and fleet project on the owner's machine stops holding plaintext secrets entirely — they hold revocable Personas-issued handles, and every real API call flows through the vault's audited, rate-limited, anomaly-scored proxy.
- **Feasibility**: high
- **Time-horizon**: months
- **Why it's a moonshot**: Today the vault protects credentials *inside* Personas while the owner's other 15+ repos still scatter `.env` files, firebase JSONs, and PATs across disk (the memory files literally carry standing "revoke firebase json" warnings). This flips the product's identity: Personas stops being "a desktop app with a vault feature" and becomes the **credential authority for everything the owner runs** — a local-first 1Password-for-agents where secrets are born in the vault, never leave it in plaintext, and every consumption event is attributed to a named consumer identity. In the agent era, "which agent used which credential to do what" is the single most valuable trust primitive nobody ships for individuals — only enterprises get this (Vault/Doppler), and none of those understand agents, scopes-per-persona, or blast radius.
- **What exists today**: Nearly every organ already exists — disconnected:
  - `src-tauri/src/engine/api_proxy.rs` — credential-authenticated HTTP proxy with per-credential token-bucket rate limiting + latency/error metrics (resolve → execute → audit pattern).
  - `src-tauri/src/engine/management_api.rs` — axum HTTP server (:9420) already gated by `external_api_keys` Bearer tokens with scopes, expiry, origin binding, per-key audit trail (`core/src/models/external_api_key.rs` — SHA-256 hash only, one-time plaintext reveal).
  - `src-tauri/src/commands/credentials/mcp_gateways.rs` + `mcp_tools.rs` — MCP gateway that already exposes Personas as a credential/tool provider to external MCP clients.
  - `src/api/credentials/scopedResources.ts` — credential pinning to sub-resources; `src-tauri/src/engine/rotation.rs` — windowed-anomaly rotation engine with per-credential locks; `src-tauri/db/src/repos/resources/audit_log.rs` — the audit backbone; `src/features/vault/sub_dependencies/BlastRadiusPanel.tsx` — revocation impact analysis UI; `src/features/vault/sub_catalog/components/foraging/` — already scans dotfiles/CLIs for stray secrets.
- **Path to implementation**:
  1. Add a `/api/proxy/{credential_ref}` route to `management_api.rs` that forwards into `api_proxy.rs`'s existing engine, enforcing the caller key's scopes ∩ the credential's `scoped_resources` — this makes any external process able to *use* a credential without ever seeing it. Doable now; both halves exist.
  2. Mint per-consumer identities: extend `external_api_keys` scopes to reference credentials/connectors (`cred:github:use`), and add a `personas creds` CLI/MCP verb ("give me a handle for Sentry") that returns a short-lived derived key, not the secret.
  3. Turn foraging inside-out: after importing a discovered secret, offer "quarantine the original" — rewrite the source `.env` to a broker reference (`PERSONAS_CRED=github/main`) + a tiny shim, so foraging becomes *migration*, not just import.
  4. Wire consumption events into the anomaly scorer and blast-radius graph: every proxied call becomes a `credential_dependents` edge, making the D3 graph reflect *live reality* instead of declared bindings, and making one-click revoke → rotate → re-issue safe.
  5. Ship a "Broker" dashboard tab: per-consumer activity, plaintext-exposure count on machine (target: zero), kill-switch per consumer.
  6. Extend over the P2P enclave (`src-tauri/engine/src/identity.rs`, `enclave.rs`) so a second device/teammate consumes credentials through the same broker without secret material ever syncing.
- **Dependencies**: management API server, api_proxy engine, external_api_keys + audit repos, scoped resources, rotation engine, foraging; optional: p2p feature flag for multi-device.
- **Risks**: (1) Latency/availability — if the Personas app isn't running, every dependent project's API calls die; needs a headless broker mode or graceful degradation. (2) Compatibility tail — SDKs that do SigV4 signing or websockets can't be naively proxied; must scope v1 to Bearer/API-key connectors. (3) Localhost HTTP is an attack surface — key theft from a rogue local process reduces (but doesn't eliminate) the win; mitigated by origin binding + short expiry + per-key rate limits already in the model.
- **What changes if we ship it**: The recurring "⚠ revoke firebase json" class of problem becomes structurally impossible; the owner's fleet of projects shares one rotating, audited, blast-radius-aware identity plane, and Personas becomes infrastructure other tools depend on — the hardest kind of product to displace.

## 2. The Living Connector Network — self-healing autonomous credential acquisition as a shared moat
- **Tier**: 1 (10x category-defining)
- **Category**: data-moat
- **Impact**: "My persona needs Sentry + Supabase + GitHub" goes from a 40-minute portal-clicking session to a single consented click — the vault acquires, verifies, and *keeps alive* working credentials autonomously, powered by a signed, community-updated registry of acquisition recipes that no competitor can replicate without the usage data.
- **Feasibility**: medium
- **Time-horizon**: quarters
- **Why it's a moonshot**: The vault already contains five independent acquisition pathways — AI design, Playwright harvesting, foraging, ambient auth detection, and guided negotiation — but each is a manual, user-initiated, fire-and-forget tool, and what they learn dies locally. The moonshot is closing the loop: acquisition becomes a *planner* that chains the pathways automatically, every success distills into a versioned recipe, every failure (healthcheck 401, rotation break, portal redesign) triggers autonomous re-acquisition — and recipes are cryptographically signed and shared across installs. Developer portals are the last un-automated frontier of agent infrastructure precisely because they change constantly; a network that heals itself from every user's failures is the only durable answer, and it compounds — the classic data-moat shape.
- **What exists today**:
  - `src-tauri/src/commands/credentials/auto_cred_browser.rs` — Claude CLI + Playwright MCP session that navigates a connector's dashboard and extracts API keys (10-min cap, 500-tool-call cap, live progress events, guided mode with `USER_INPUT:`/`OPEN_URL:` protocol).
  - `src-tauri/src/commands/credentials/credential_recipes.rs` + `credential_design.rs`, `schema_proposal.rs` — recipe store (fields, healthcheck, setup instructions, usage counter, `source` provenance) and AI connector-schema generation from OpenAPI/description.
  - `src-tauri/src/commands/credentials/foraging.rs` + `auth_detect.rs` — environment scanning and ambient-auth discovery; `src/features/vault/sub_catalog/components/negotiator/` — AI-guided step-by-step setup.
  - `src-tauri/src/engine/rotation.rs` + `healthcheck.rs` + `connector_strategy.rs` — the failure detector: windowed 5m/1h/24h anomaly scoring with transient-vs-permanent classification already knows *when* a credential died and *why*.
  - `src/api/signing/index.ts` (document sign/verify) + `src-tauri/engine/src/identity.rs` — the trust primitives for signed recipe distribution; `src/features/vault/sub_catalog/components/picker/useRecipeIndicators.ts` — recipe-awareness already surfaces in the catalog.
- **Path to implementation**:
  1. Build the **acquisition planner**: a single `acquire_credential(connector)` command that runs the cheapest-first cascade — foraging hit? → ambient CLI auth? → cached recipe replay via AutoCred? → fresh AI design + harvest → healthcheck-gated save. All five stages exist as commands today; this is orchestration plus one consent dialog. Doable now.
  2. **Distill on success**: when an AutoCred session passes healthcheck, have the same Claude session emit a machine-replayable acquisition script (portal URL sequence, selectors, field mapping) into `fields_json`/`setup_instructions` of the recipe — turning one $0.50 harvesting run into a near-free replay forever.
  3. **Self-heal on failure**: wire `rotation.rs`'s permanent-failure classification (401/403) to enqueue re-acquisition through the planner instead of just banner-ing `ReauthBanner.tsx` — the user wakes up to "Sentry credential was dying; re-acquired and rotated, 1 approval pending."
  4. **Sign and sync recipes**: recipes get signed with the device identity keypair and published to a registry (start: a plain GitHub repo of signed JSON; later: the P2P layer). Import path verifies signatures + strips anything secret-shaped through `core/src/redact.rs` before publish.
  5. **Close the flywheel**: recipe replay failures (portal changed) auto-open a repair AutoCred session; the repaired recipe is republished with a version bump — the network heals faster than portals break.
- **Dependencies**: Claude CLI + Playwright MCP availability, recipe repo + signing modules, rotation/healthcheck engine, redaction pass; external: a registry host (GitHub repo suffices for v1).
- **Risks**: (1) ToS friction — some providers prohibit automated portal interaction; needs a per-connector policy flag and consent-forward UX. (2) Harvest reliability — portals with CAPTCHA/2FA will always need the guided fallback; the planner must degrade gracefully rather than promise full autonomy. (3) Supply-chain of recipes — a malicious shared recipe could steer harvesting to a phishing portal; signature + domain-pinning (recipe may only navigate its connector's registered domains, enforced via the existing URL-safety layer) is mandatory from v1, not later.
- **What changes if we ship it**: Credential setup — the #1 onboarding cliff for the whole product (the "Onboarding to First Run" journey routes through credential-negotiator) — becomes a background process; the 130-connector catalog becomes a living, self-repairing, community-maintained asset that grows more valuable with every install, which is the moat.
