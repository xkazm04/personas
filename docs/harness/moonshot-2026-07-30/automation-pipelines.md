# Moonshots — Automation & Pipelines

## 1. The Self-Wiring Fabric — automation that automates itself
- **Tier**: 1 (10x category-defining)
- **Category**: intelligence
- **Impact**: The event bus stops being a passive switchboard the user must hand-patch and becomes a system that observes its own traffic, mines recurring cause→effect patterns, and proposes — then, on Full autopilot, commits — new trigger routes itself, so the automation surface grows without the user opening the Chain Studio.
- **Feasibility**: medium
- **Time-horizon**: months
- **Why it's a moonshot**: Every automation platform on earth (Zapier, n8n, Make, Personas today) shares the same ceiling: a human must *notice* a repeatable pattern and *manually wire* it. The moonshot inverts that. Personas already has the three raw ingredients nobody else combines: a full local event log (`persona_events`), a full execution/outcome log (`executions`, `schedule_runs`, dead-letter), and — uniquely — the graduated autonomy ladder (`off/measure/suggest/full`) already built and trusted in `autopilot.rs`. Mining "user manually executed persona X within 10 minutes of event Y, five times this month" into a ghost patch-cable the user accepts with one click is the difference between an automation *tool* and an automation *colleague*. It also compounds: every accepted or rejected suggestion is training signal, exactly the pattern `recipe_suggestion_log` already established.
- **What exists today**:
  - Pattern substrate: `src-tauri/src/engine/composite.rs` already scans the recent event window every tick and — critically — computes **partial-match diagnostics** (`PartialMatchResult`, per-condition `ConditionStatus`) for near-miss evaluations. The mining loop is a sibling of code that exists.
  - Autonomy ladder: `src-tauri/engine/src/autopilot.rs` + `autonomy.rs` (per-project `off/measure/suggest/full` with a `Capability` gate enum designed to be extended).
  - Commit path: `src/features/triggers/sub_studio/libs/studioCommit.ts` + `studioDraftModel.ts` already turn a draft link (source event → target persona + condition) into a real `create_trigger` input; the Chain Studio patchbay (`TriggerStudioCanvas.tsx`, `StudioPatchbay.tsx`) is the natural surface for rendering *suggested* ghost cables next to committed ones.
  - Safety rails, all pre-built: trigger dry-run (`dryRunTrigger` in `useTriggerOperations.ts`), per-trigger rate limits (`sub_speed_limits/RateLimitDashboard.tsx`), dead-letter queue (`sub_dead_letter/DeadLetterTab.tsx`), trigger health sparklines (`TriggerHealthSparkline.tsx`).
  - Suggestion-scoring precedent: `src-tauri/engine/src/recipe_matcher.rs` (weighted-Jaccard with a calibrated threshold) and `recipe_suggestion_log` show the propose→log→learn loop pattern already in the codebase.
- **Path to implementation**:
  1. **Now**: add a `pattern_miner.rs` next to `composite.rs` — a background tick that scans `persona_events` joined with `executions` for co-occurrence pairs (event type E followed by manual execution of persona P within window W, ≥N times) and writes candidate rows to a new `automation_suggestions` table. Pure read-side, zero risk.
  2. Extend `autopilot::Capability` with `AutomationSuggestion` and `AutomationCommit`, gated at `suggest` and `full` respectively — a ~20-line change by design of that module.
  3. Render candidates as dashed "ghost cables" in the Studio patchbay (`StudioPatchbay.tsx`), with the evidence trail (the N historical co-occurrences) in a drawer; accept routes through the existing `studioCommit.ts` path, reject logs to the suggestion table.
  4. Widen mining beyond co-occurrence: use composite near-miss diagnostics ("this composite fired 4/5 conditions 12 times — suggest relaxing to OR"), dead-letter clusters ("this event type always dead-letters — suggest a route or a mute"), and schedule-health data ("this cron fails every Monday 9am — suggest shifting or adding a retry chain").
  5. `full` mode: auto-commit suggestions that pass a dry-run and start them under a conservative auto-applied rate limit, with an undo window surfaced through the existing notification channels.
  6. Feed accept/reject history back into the candidate scorer (same evolution `recipe_matcher.rs` doc-comments already plan: cheap prefilter → LLM refinement via the `ai_artifact_flow` streaming pattern used by `recipe_generation.rs`).
- **Dependencies**: internal only for steps 1–5 (`persona_events`/`executions` repos, autopilot settings, Studio commit path, dry-run). Step 6 optionally uses the existing local LLM/CLI streaming stack.
- **Risks**: (1) False-positive suggestions erode trust fast — the evidence drawer and a high initial threshold are load-bearing, not polish. (2) Auto-commit in `full` mode can create feedback loops (a suggested trigger's own executions becoming mining input) — mined routes must be tagged and excluded from their own evidence. (3) Co-occurrence mining on a solo user's data is sparse; needs honest "not enough signal yet" states rather than stretched inferences.
- **What changes if we ship it**: Personas becomes the first automation platform where the wiring diagram grows itself — the user's role shifts from electrician to editor, and every other feature (recipes, schedules, teams) inherits a system that notices what the user does repeatedly and offers to own it.

## 2. The Automation Compiler — one IR, every platform
- **Tier**: 1 (10x category-defining)
- **Category**: platform
- **Impact**: Personas becomes the portable source-of-truth for automations: ingest a workflow from n8n/Zapier/Make/GitHub Actions, hold it as a platform-neutral IR bound to the local credential vault, and compile it back out to *any* of those targets — turning today's one-way n8n import wizard plus three one-off adapters into a "write once, deploy anywhere" automation compiler.
- **Feasibility**: medium
- **Time-horizon**: quarters
- **Why it's a moonshot**: Automation platforms are silos by business model — your Zapier zaps are hostage to Zapier. Personas already has, uniquely, *both halves* of the escape hatch built as separate features that have never been introduced to each other: a full multi-step **import** pipeline (the n8n wizard: parse → entity review → connector/credential gap analysis → transform to persona) and a full **export/deploy** layer (`platforms/deploy.rs` dispatching LLM-designed `DesignResult`s to GitHub Actions, n8n, and Zapier adapters). Fusing them around one neutral IR makes Personas the *compiler* — the layer that owns the definition while rented platforms merely run it. That is a category no desktop app occupies, it is a genuine data-moat (the IR + vault binding is the asset), and it multiplies the owner's leverage: every workflow authored anywhere becomes runnable everywhere, including locally as a persona.
- **What exists today**:
  - Import half: the entire n8n wizard — `src/features/templates/sub_n8n/hooks/useN8nWizard.ts` (orchestration over `transform_n8n_workflow` / `get_n8n_design_data` IPC), `steps/upload/` (file/paste/URL ingestion already labeled with **platform origin**), and crucially `edit/connectorMatching.ts` + `edit/credentialGapAnalysis.ts` + `edit/protocolParser.ts` — ranked credential-to-connector matching against the vault, exactly the "linker" stage a compiler needs.
  - Export half: `src-tauri/src/engine/platforms/{mod,deploy,github,n8n,zapier}.rs` — a working deploy-target abstraction (`DeployAutomationInput` → platform dispatch → `PersonaAutomation` row with `platform_url`/`webhook_url`), plus `commands/tools/automation_design.rs` (LLM already emits a platform-targeted `DesignResult`) and `deploy_automation.rs`.
  - IR precedent: `src-tauri/engine/src/template_v3.rs` already bridges a rich nested schema down to the flat `AgentIr` the backend consumes, and `compilation_pipeline.rs` explicitly advertises that adding a new compiler (its own doc-comment suggests "TriggerCompiler") requires only implementing the `CompilationPipeline` trait.
  - Round-trip bookkeeping: `automation_runs`/`persona_automations` tables, `n8n_sessions` repo (`db/repos/resources/n8n_sessions.rs`), and template checksums (`template_checksums.rs`) for IR integrity.
- **Path to implementation**:
  1. **Now**: extract the platform-neutral IR. Define `AutomationIr` in `src-tauri/core/src/models/` (steps, triggers, connector requirements, credential slots) and make the existing n8n transform emit it as an intermediate — the wizard's current output becomes `n8n → IR → persona` instead of `n8n → persona`. Pure refactor of an existing flow; nothing user-visible changes.
  2. Implement the first *emitter*: `IR → n8n` through the existing `platforms/n8n.rs` adapter, and prove lossless-enough round-trip (`n8n → IR → n8n`) on the wizard's own test workflows (`testReducer.ts` / `test_n8n_workflow` already give the harness).
  3. Add a second *frontend*: a Zapier/Make JSON parser feeding the same wizard UI — the upload step's `PlatformLabels.tsx` and the ingestion-hook trio were built for exactly this multiplicity; connector gap analysis is reused unchanged because it operates on parsed connector metadata, not n8n specifics.
  4. Add emitters for GitHub Actions (workflow YAML via `platforms/github.rs`) and "local persona" (IR → `AgentIr` via a new `CompilationPipeline` impl, per the trait's own extension note) — at which point any imported workflow can *also* run natively with vault credentials, no cloud platform needed.
  5. Ship the "recompile target" UX: a deploy-target picker on any automation (`deploy_automation.rs` path) showing per-target credential gaps (reusing `credentialGapAnalysis.ts`) before committing.
  6. LLM gap-filler for semantic mismatches: when a node has no clean mapping on the target platform, route through `automation_design.rs`'s existing design flow to synthesize the equivalent — with the diff shown for approval, mirroring `recipe_versioning`'s accept/revert pattern.
- **Dependencies**: internal — n8n wizard stack, platform adapters, credential vault + connector matching, `CompilationPipeline` trait. External — n8n/Zapier/Make/GitHub APIs (all already integrated read- or write-side somewhere in the codebase), and platform export formats (n8n JSON and GH Actions YAML are open; Zapier/Make export is the weakest link).
- **Risks**: (1) IR expressiveness is the classic compiler trap — n8n's node semantics don't map 1:1 to Zapier or Actions; must accept lossy compilation with explicit per-step "untranslatable, LLM-assisted" markers rather than pretending fidelity. (2) Zapier/Make lack clean workflow-export APIs, so those frontends may be paste/scrape-grade for a while. (3) Maintenance surface: each platform's schema drifts; checksummed IR + conformance tests per emitter (the `template_checksums.rs` pattern) is the mitigation.
- **What changes if we ship it**: Automations stop belonging to platforms and start belonging to the user — Personas holds the canonical, vault-bound definition and treats n8n, Zapier, and GitHub Actions as interchangeable compile targets, which is a moat, a migration magnet, and the strongest possible answer to "why is this a desktop app".
