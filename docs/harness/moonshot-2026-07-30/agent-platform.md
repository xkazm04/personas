# Moonshots — Agent Platform

## 1. The Agent Mesh — every Persona becomes a signed, addressable node in a federated agent network
- **Tier**: 1 (10x category-defining)
- **Category**: platform
- **Impact**: Personas stops being a desktop app that *runs* agents and becomes the trust-and-routing fabric through which agents — yours, your peers', and external A2A/MCP agents — discover, verify, and delegate to each other; every persona built in the editor is instantly a network citizen.
- **Feasibility**: medium
- **Time-horizon**: quarters (first delegation working in weeks)
- **Why it's a moonshot**: Today the A2A surface is explicitly half-built: `src-tauri/engine/src/a2a/mod.rs` states "Future work: client.rs — outbound A2A consumer, streaming via message/stream, per-key scope-based persona allowlists". The inbound side already serves spec-compliant AgentCards and JSON-RPC `message/send` (`a2a/types.rs`), and — critically — the trust primitives for a *federated* network already exist in scattered, unconnected pieces: Ed25519-style document signing with peer identity (`db/src/repos/resources/signing.rs`), exposure controls with `access_level`/`requires_auth`/`expires_at` and import provenance with `signature_verified` + `bundle_hash` (`db/src/repos/resources/exposure.rs`), a versioned portable persona bundle (`commands/core/import_export.rs`), and a live P2P layer (`engine/src/p2p/`). No one has shipped a *local-first, cryptographically-verified* agent network — cloud agent platforms can't, because they own identity centrally. Personas can, because the signing keys, the personas, and the runtime all live on the user's machine. This is the difference between "an app with 100 agents" and "a protocol node in a mesh of every builder's agents" — network effects the current single-player app structurally cannot have.
- **What exists today**:
  - `src-tauri/engine/src/a2a/mod.rs`, `a2a/types.rs` — inbound A2A server (AgentCard, message/send, tasks/get/cancel); outbound client is an explicit TODO.
  - `src-tauri/src/engine/management_api.rs` — HTTP dispatch layer hosting the A2A routes.
  - `src-tauri/db/src/repos/resources/signing.rs` — signature store with `signer_peer_id`, `signer_public_key_b64`, `file_hash`.
  - `src-tauri/db/src/repos/resources/exposure.rs` — `ExposedResource` (access levels, auth, expiry) + `ResourceProvenance` (peer origin, bundle hash, signature verification) — the ACL and provenance model for shared resources, currently underused.
  - `src-tauri/src/commands/core/import_export.rs` — versioned `.persona.json` bundle with a real migration contract.
  - `src-tauri/engine/src/p2p/{types,connection}.rs` — peer connections already speak an outbound protocol.
  - `src-tauri/db/src/repos/resources/tools.rs`, `src/api/agents/mcpTools.ts` — tool/MCP catalog a remote persona can be projected into as "just another tool".
- **Path to implementation**:
  1. Build `a2a/client.rs` (the file the module doc already names): fetch a remote AgentCard, send `message/send`, poll `tasks/get`. Wire it as a new tool type in `tools-connectors-repo` so any persona can list a remote agent as a callable tool — remote delegation drops straight into the existing prompt-assembly tool-hint path (`engine/src/prompt/capabilities.rs`).
  2. Surface it in the editor: a "Delegates to" section in `persona-editor` that pastes an A2A URL, renders the remote AgentCard, and persists the binding — Personas-to-Personas across two machines is the first demo.
  3. Sign persona export bundles: run `import_export.rs` bundles through `signing.rs` (hash + peer keypair), and verify + record `ResourceProvenance` on import. Now shared personas carry verifiable authorship and tamper-evidence.
  4. Gate inbound A2A with `exposure.rs`: exposing a persona creates an `ExposedResource` with access level and expiry; the A2A dispatcher checks it (this is the "per-key scope-based allowlists" TODO, done properly with existing tables).
  5. Peer directory over the existing `p2p` layer: peers exchange signed AgentCard lists, giving a "network" tab of every agent your trusted peers expose — discovery without any central server.
  6. Add `message/stream` (SSE) so delegated calls stream into the existing execution trace UI like local middleware stages.
- **Dependencies**: `management_api.rs` HTTP server, `p2p` engine module, signing keypair management, `tools-connectors-repo`, prompt-assembly capabilities module; no new external services (the A2A spec is the interop bet).
- **Risks**: (1) Security blast radius — an inbound network surface on a desktop app must get authn/rate-limiting right or it becomes the app's biggest liability; exposure ACLs must default-deny. (2) A2A spec adoption is still early; mitigated by MCP projection as the fallback interop path. (3) Cross-machine delegation debugging (latency, partial failure) could swamp the solo owner — streaming traces (step 6) must land early, not last.
- **What changes if we ship it**: A persona built once on one machine is callable — verified, permissioned, and traced — from every other project, machine, and external LLM host the owner touches. Personas becomes infrastructure other agents stand on, not a silo they live in.

## 2. Darwin Mode — close the evolution loop with measured fitness so the fleet improves itself from its own execution history
- **Tier**: 1 (10x category-defining)
- **Category**: intelligence
- **Impact**: Every real execution across the fleet becomes selection pressure: personas that run often get automatically challenged by variants evaluated on *measured* real-workload fitness, and provably-better variants promote through the existing governance gate — the owner's agents get better while they sleep, compounding across all projects.
- **Feasibility**: medium
- **Time-horizon**: months
- **Why it's a moonshot**: The genetic scaffold is remarkably complete but the loop is *open at its most important joint*: `core/src/models/genome.rs` says offspring fitness "is an *inherited* (mid-parent) prediction, NOT a measured evaluation... Direct offspring evaluation is a deferred follow-up." `EvolutionPolicy` (`core/src/models/evolution.rs`) already has enabled/mutation_rate/improvement_threshold/promotion counting and two mutation strategies ("mechanical" and "critique"), yet promotion decisions rest on predicted numbers — evolution that never actually measures its children is astrology, not selection. Meanwhile every ingredient of a real fitness function already exists in this group: output assertions (behavioral contracts, `agent-settings` / `output_assertions` table), lab runs and A/B matrix builds (`labSlice.ts`, `matrixBuildSlice.ts`), scheduled health checks (`healthCheckSlice.ts`), budget enforcement, execution traces, and the memory claims/review pipeline (`db/src/repos/core/memory_claims.rs`) as a template for human-gated promotion. This is "finish and amplify" at maximum leverage: connect five shipped systems into one closed loop and the product's core claim flips from "build and run agents" to "agents that demonstrably improve with use" — a data moat no fresh install can copy, because fitness history *is* the moat.
- **What exists today**:
  - `src-tauri/core/src/models/genome.rs` — `GenomeBreedingRun`/`GenomeBreedingResult` with adoption tracking; fitness explicitly predicted-only.
  - `src-tauri/core/src/models/evolution.rs` — `EvolutionPolicy` + `EvolutionCycle` (incumbent vs winner fitness, promotion flag, min_executions_between).
  - `src/stores/slices/agents/labSlice.ts`, `matrixBuildSlice.ts`, `healthCheckSlice.ts`, `budgetEnforcementSlice.ts` — offline experimentation, multi-model variant builds, scheduled checks, spend caps (the safe evaluation sandbox).
  - `src/features/agents/sub_settings/components/PersonaAssertionsSection.tsx` + `output_assertions` — machine-checkable behavioral contracts, i.e. the objective component of fitness.
  - `src-tauri/db/src/repos/core/memory_claims.rs`, `memory_review_proposal.rs` — the claim → review → promote pattern to reuse for variant promotion.
  - `src-tauri/db/src/repos/resources/persona_change_log.rs` — audit trail so every evolved change is attributable and revertible.
  - `src-tauri/db/src/memory_recall.rs` — decay-scored value model; the same discipline (pure, deterministic scoring) to apply to fitness.
- **Path to implementation**:
  1. Ship measured fitness: after a breeding/evolution cycle, replay a fixture set (fixtures already exist per use-case in `agent-use-cases`) through each offspring as lab runs, scoring assertion pass-rate + cost + latency from the trace — write it into the existing `fitness_json`/`fitness_overall` fields, replacing the mid-parent prediction. This is a contained Rust change plus a lab-run driver; doable now.
  2. Build the challenger harness: `EvolutionPolicy.enabled` personas get a shadow variant evaluated on the *last N real inputs* (replayed under budget caps), not just synthetic fixtures — fitness against the actual workload.
  3. Promotion-as-proposal: route "winner beats incumbent by improvement_threshold" through a review proposal (mirroring `memory_review_proposal`), surfaced in the companion decision layer (`companion-decision/useDecisionQueue.ts`) so the owner approves promotions with one numbered voice/tap choice; log to `persona_change_log`.
  4. Population view: a fleet-level "evolution board" on `persona-overview-director` (VerdictTrendCell already trends verdicts) showing fitness trajectories, active challengers, and promotion history per persona.
  5. Cross-persona trait extraction: when a mutation wins repeatedly (e.g. a rewritten prompt segment or tool ordering), diff it into a named "trait" and offer it to sibling personas in the same group — turning one persona's learning into fleet-wide gains via `recipes-repo` as the trait store.
  6. Autopilot tier: for personas with strong assertion coverage, allow auto-promotion under a rollback watchdog (auto-revert via change log if post-promotion assertion pass-rate drops).
- **Dependencies**: lab run executor, fixtures per use-case, output-assertion evaluator, budget enforcement (hard requirement — evolution burns tokens), companion decision queue, persona_change_log; Claude API via `engine/src/provider/claude.rs` for critique-mode mutations.
- **Risks**: (1) Fitness gaming — variants can overfit fixtures; mitigated by mixing real-workload replay (step 2) and rotating fixture sets. (2) Cost: N variants × M fixtures × generations is real money; budget slice must cap cycles, and cheap models should score before expensive ones confirm. (3) Silent behavioral drift from auto-promotion eroding trust — hence proposal-gated by default, autopilot only behind assertion coverage + rollback.
- **What changes if we ship it**: The persona list stops being a static inventory and becomes a living population with visible fitness trajectories; the owner's role shifts from hand-tuning prompts to setting objectives and approving promotions, and every project running Personas agents compounds quality automatically.
