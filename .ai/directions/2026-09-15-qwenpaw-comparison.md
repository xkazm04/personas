## The asymmetry that governs every verdict below

QwenPaw has two sides. For its own agents it **owns the loop**: `agents/react_agent.py:1037` runs the stop hook on every iteration, and a gate can defer a stop until the tool results are in (`loop/gates/runner.py:156-226`). For Codex and qoder it is a **wrapper**, like personas. personas owns no loop, and its own code says so: *"personas runs the CLI under `-p` and has no per-call seam inside the spawned binary"* (`src-tauri/src/engine/runner/hooks/registry.rs:88-91`). So every point about iteration gates, context folds or tool deadlines is a candidate for `different forces`. The points where QwenPaw is a wrapper (approvals, resume, runtime pooling) and the points about loops personas does own (deliberation, healing chains, schedules) are where the comparison has teeth.

**Headline: four of the design record's seeded personas contrasts are wrong in a way that matters, and each correction sharpens a finding.**

1. **personas does not uniformly classify before `--resume`.** `is_resume_safe` (`src-tauri/core/src/error_taxonomy.rs:436-457`) has exactly one production caller (`src-tauri/engine/src/ai_healing.rs:110`). The companion build turn does what the seed attributes to QwenPaw: on a string-matched "no conversation found" it clears the pointer and silently retries with a fresh session (`src-tauri/src/companion/session/build_turn.rs:164-167`, matcher `cli.rs:514-519`). The two trees also answer different questions. personas asks *is the prior failure baked into the transcript?*; QwenPaw reacts to *the resume call itself failed* (`harnesses/codex/adapter.py:555-567`). See §4.3.
2. **The schedule auto-pause is not "like" the mail guard.** QwenPaw pauses after **3 consecutive** failures and fails **closed** on unreadable state (`app/mail/processing_guard.py:17`, `:74-80`). personas pauses on a **≥90% rate over ≥12 runs in 168 h** (`src-tauri/src/engine/background/scheduler.rs:310-327`) and fails **open** when the outcome query errors: *"outcome query failed, firing anyway"* (`:926-929`). A daily schedule fires 7 times in the window, so it can never reach the 12-run floor. See §5.1 and §5.2.
3. **`manual_review` is a queue with no waiter.** Every production raise site is post-hoc: output assertions (`src-tauri/engine/src/output_assertions.rs:559`), the director (`src-tauri/src/engine/director.rs:1908`), and a protocol message parsed from finished output (`src-tauri/engine/src/parser.rs:627`). Nothing a running child could block on exists. The nearest human wait is a team assignment's `awaiting_review`, and that pauses *between* steps (`src-tauri/core/src/models/team_assignment.rs:26-27`). See §3.1.
4. **No permission-prompt CLI flag is documented anywhere in personas' tree.** `git grep -i permission-prompt` returns only voice-dictation hits, and no `claude --help` transcript is recorded. The tree does record why stdin cannot carry the round trip: *"control requests need `--input-format stream-json`; personas pipes plain text on stdin"* (`src-tauri/engine/src/provider/claude.rs:106-107`). The MCP sidecar is therefore the only bidirectional channel already inside the `-p` child. Whether the CLI can delegate a permission decision to it is an open question for a spike, not a fact. See §3.1 and ranked feature 3.

A fifth finding came from personas' own tree. **A resumed spawn carries no spend bound**: the resume builder deliberately leaves out `--max-budget-usd` (`src-tauri/engine/src/prompt/cli_args.rs:351-355`), and the aggregate ledger registers only lab, evolution and pipeline runs (`src-tauri/engine/src/test_runner/modes.rs:61`, `src-tauri/src/engine/evolution.rs:213`, `src-tauri/src/engine/pipeline_executor.rs:831`). QwenPaw's rule that token usage never resets inside a turn is the rule that closes it (§1.4).

## Tests to initiate

Each is paired and names its instrument and the number that would move.

**T1: Do resumed spawns overspend the persona's cap?** (§1.4) *Instrument*: `persona_executions.cost_usd` summed per healing chain (the rows spawned through `--resume`) against the persona's `max_budget_usd`, over the live database. *Number that would move*: chains whose summed cost exceeds the cap. Today that is unmeasured; the target after ranked feature 1 is zero. *Paired arm*: fresh spawns for the same personas in the same window must show the same per-spawn exceed rate before and after, or the change has altered the fresh path it was meant to leave alone.

**T2: Which schedules can the auto-pause never reach?** (§5.1) *Instrument*: parse every enabled schedule trigger's cron and count fires per 168 h, then replay `trigger_outcomes_in_window` history under two arms: the rate rule (today) and rate-or-3-consecutive. *Numbers that would move*: (a) triggers under 12 fires per window, which can never trip today; (b) pauses the consecutive arm adds. *Paired arm*: false pauses, counted as a pause followed by a success within the next three fires, must stay at or below the rate arm's own count.

**T3: How often does the companion silently drop its context?** (§4.3) *Instrument*: a counter at `build_turn.rs:166` beside the existing refusal count at `ai_healing.rs:110`. *Number that would move*: companion re-threads per 100 turns, which is invisible today. *Paired arm*: healing-door refusals over the same period. If re-threads are zero over two weeks, §4.3 downgrades to `keep ours`.

**T4: Can the print-mode child hand a permission decision to the sidecar at all?** (§3.1) *Instrument*: record the installed CLI's `claude --help` output into the tree, then run one persona twice on a prompt that makes a single Bash call. *Arm A*: `--dangerously-skip-permissions` (today). *Arm B*: whatever documented delegation the help text shows, pointed at a stub personas-mcp tool that answers deny. *Number that would move*: Bash calls that executed in arm B. The target is 0, and a non-zero count means the wire is not a boundary. If the help text documents nothing, the number is not measurable and the test ends there as a recorded negative.

**T5: Do failed runs repeat themselves?** (§1.8) *Instrument*: replay stored stream output for 30 days of terminal executions and hash `(tool name, input)` over a sliding window of 3. *Number that would move*: the share of `failed` or timed-out runs containing a repeated window. *Paired arm*: the same share among `completed` runs. If the two are within a few points, repetition is not a failure signal here and §1.8 is dropped.

## Features, ranked, with why `scope.does` admits each

`scope.does`: *"run local AI agent personas over wrapped CLIs, local-first storage, one operator per install"*; *"observe runs - cost, health, traces - and tune routing from evidence"*.

**1. A resumed spawn inherits the remaining spend bound** (§1.4) → subject `spend-ceilings` / `session-continuation`.
Admitted by *"observe runs - cost"*: a healing chain whose continuation carries no `--max-budget-usd` spends against no cap the operator set, and personas' own resume builder names the question and leaves it open (`cli_args.rs:351-355`).
- *First context contains*: the resume builder (`cli_args.rs:280-360`), the healing spawn path (`ai_healing.rs:103-112` and its `spawn_healing_chain` caller), the per-spawn flag site (`cli_args.rs:130-137`), and the spend query the schedule gate already shares (`get_monthly_spend`, `scheduler.rs:276-287`). - *Measurable*: the share of resumed spawns carrying `--max-budget-usd` when the persona has a cap, 0% today and 100% after. T1's exceed count goes to zero.

**2. A consecutive-failure arm on schedule auto-pause, and a record when the monitor fails open** (§5.1, §5.2) → subject `job-coordination` / `circuit-breakers`.
Admitted by *"observe runs - health"*: a daily schedule failing every morning re-spends tokens forever and never produces the incident the rate monitor was built to raise.
