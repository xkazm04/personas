# personas vs. `exoharness/exo` — peer study (agent + harness architecture)

- **Source**: `github.com/exoharness/exo`, clone `C:/t/intake-exo`, pinned `7801005`. Read read-only; nothing in this study was built.
- **Written**: 2026-09-04 by intake run `intake-exo`, Phase 7.6 (peer shape). No ledger row.
- **Paths**: exo anchors are relative to `C:/t/intake-exo`; personas anchors are relative to the personas root.
- **Why a comparison and not three proposals.** `.ai/manifest.yaml:97` fixes personas at *"run local AI agent personas over wrapped CLIs, local-first storage, one operator per install"*. exo is an agent harness that runs locally, serves one operator, and wraps vendor CLIs — a Codex app-server over JSON-RPC (`exoharness/typescript/codex/app-server.ts:1-40`) and the Cursor SDK (`exoharness/typescript/cursor/sdk.ts`). Same class of system, same week of the field. That makes almost every axis comparable, which is what a study is for and what a direction pass is not.
- **Verdicts** come from the closed set `adopt` / `adapt` / `keep ours` / `different forces`. Every one carries its reason.

**Verdict tally: 45 points — 11 `adopt`, 7 `adapt`, 22 `keep ours`, 5 `different forces`.**

---

## The asymmetry that governs every verdict below

exo owns its loop **twice**. It runs a native Responses/Anthropic turn loop (`exoharness/typescript/model-runtime/turn-loop.ts:101-140`) *and* it wraps a vendor CLI as a warm app-server session, keeping a bidirectional protocol log (`exoharness/examples/typescript/codex-harness.ts:139`, `:179`). personas owns neither, and the tree states it in code rather than in a doc: *"personas runs the CLI under `-p` and has no per-call seam inside the spawned binary to attach them to"* (`src-tauri/src/engine/runner/hooks/registry.rs:88-91`), backed by `.claude/codebase-stack.md:28` — *"the application does not implement an LLM client."*

So exo is a **superset peer**, not a mirror. Every point that touches the message array, the round counter, the prefix cache or the tool schema is a candidate for `different forces` — and the points that are *not* protected by that asymmetry are exactly where exo has something to give: the outbox, the artifact spill, the price table, the sandbox scope ladder, and the compare-and-swap it built in one place and skipped in another.

**Headline — the seed read is right about exo and wrong about personas four times, and each correction makes the finding sharper.**

1. **personas does have a self-modification surface**, and it is better bounded than exo's — four independent code gates against one prose claim three exo documents state three different ways (§1.1). The real gap is the *declaration nobody enforces*, and it is personas' own (§1.2).
2. **The memory seed is inverted.** exo always-injects because it has no retrieval; personas has a three-stage retrieval funnel with decay half-lives and an embedding blend (§5.1). But the *concurrency* half of the seed transfers exactly, and symmetrically: **both trees built compare-and-swap in one subsystem and did not use it in memory** (§5.4). That is the strongest finding in the study.
3. **The cost seed understates exo's defect.** exo's TypeScript price model *can* price cache-creation tokens and its only call site never passes them, on a provider whose `input_tokens` excludes them — so exo prices Anthropic cache writes at **zero** (§6.3). personas stores both buckets with unusual care and prices neither, which is a display gap, not a wrong number.
4. **The most valuable finding came from personas' own tree, not from exo.** `src-tauri/engine/src/git_checkpoint.rs` implements checkpoint / snapshot / rollback / fork-from-checkpoint, hardened, and has **zero call sites** — while its own header still states the motivating problem as present (§8.4).

## 1. Self-modification and its trust root

**1.1 — Where the immutable core is, and how many answers there are.**
exo: `README.md:31` — *"The only thing it can't muck with is an event log"*. `docs/RSI.md:44-46` — the exo-harness *"is the only part of Exo which cannot be modified by the agent"*. `docs/RSI.md:62-64` then concedes it: *"Whether or not the agent can modify the exo-harness is actually a policy consideration. The system technically allows it, but… it's disallowed on the default configuration."* And the canonical launcher mounts the whole tree read-write — `exo agent mount add "$AGENT" "$ROOT_DIR" "$SELF_REPO_MOUNT_PATH" --rw` (`exo.sh:647`) — though the mount API is a typed two-state `FileSystemMountMode` (`crates/cli/src/main.rs:1700-1706`) and the read-only arm exists. A fourth answer nobody states: `delete_conversation` (`crates/exoharness/src/basic.rs:1418`) removes the "immutable" log wholesale — mitigated only by its being a runner op (`exoharness/typescript/harness/runner.ts:269`), not a model-visible tool.
personas: one surface, four bounds, all code. *"Athena treats the running app's own source checkout as a workspace… she may propose `dev_improve` dispatches"* (`src-tauri/src/companion/dev_mode.rs:1-15`), executed by `execute_dev_improve` (`src-tauri/src/commands/companion/approvals/approval_exec_dev.rs:866`). It is gated by (a) a debug-build compile gate — `cfg!(debug_assertions) && <settings row>` at `src-tauri/src/commands/companion/chat.rs:285`, re-checked in the executor at `approval_exec_dev.rs:873-879`; (b) a mandatory approval that survives the autoapprove allowlist removal (`approval_exec_dev.rs:861-862`, `approval_autopilot.rs:36-38`); (c) worktree isolation whose `backend` flag defaults to `true` because *"a wrong `false` would hot-edit the live app"* (`approval_exec_dev.rs:888-891`), merged only through a `dev_merge` handshake (`:820-833`); (d) a canonicalized cwd allowlist requiring containment in a registered `dev_projects` row (`approval_exec_fleet.rs:1079-1099`).
**Verdict: `keep ours`.** Four independent gates, each a check the compiler or the DB can see, beat one prose invariant that three documents in the same repository state three different ways and the default launcher contradicts. The transferable half is not exo's — it is §1.2.

**1.2 — The declaration nobody enforces.**
exo: the read-only mount mode exists and the canonical path never takes it (`exo.sh:647`).
personas: `.ai/manifest.yaml:38` declares `neverTouch: [src/lib/bindings/, src/i18n/generated/, src/lib/commandNames.generated.ts]` and **nothing reads it**. `.ai/doctor.mjs` parses `generatedAt`/`generatedFrom` (`:98-101`) and greps the boundaries block for a literal `TODO` (`:109`) without ever parsing `neverTouch`; `lefthook.yml`'s pre-commit jobs are `eslint-staged` (`:20`), `gitleaks-staged` (`:27`), rustfmt (`:51`) and two i18n checks (`:63`, `:75`); none of the 21 rules in `eslint-rules/` is a write-path guard; `scripts/` has no reference. The only effective protections are drift detection after the fact (`.gitlab-ci.yml:198-208` fails on a changed `src/lib/bindings/`) and a **prompt-level** instruction telling the agent generated files are off limits (`src-tauri/src/commands/companion/approvals/approval_exec_knowledge.rs:559-563`).
**Verdict: `adopt`.** Same defect, and personas' is the cheaper one to close: `.ai/doctor.mjs:109` already opens the block it declines to parse, and personas' self-modification surface (§1.1) writes into a worktree of the very tree the declaration protects. A prompt-level boundary is the one enforcement mechanism the agent can talk itself out of.

**1.3 — Reversibility as a stated default, and state as a record rather than a verb.**
exo: written as law — *"Mutations are reversible by default: prefer disabling and checkpointing over deletion… An audit record of an unrecoverable action is not a substitute for being able to undo it"* (`docs/SELF-CONTROL.md:26-29`) — and realized structurally: there is no `start_adapter`/`stop_adapter`/`restart_adapter`; *"starting is creating an enabled adapter, stopping is disabling"* (`docs/SELF-CONTROL.md:145-147`).
personas: the same instinct in three places and stated as law in none. The worktree branch is *"left for review on completion (no auto-merge)"* (`src-tauri/src/engine/runner/mod.rs:672-673`); `ExecutionIntegration` has exactly one variant, `LeaveAsBranch`, and the doc withholds a `Merge` variant on purpose — *"auto-merging into the user's real base branch would mutate their repo without consent"* (`src-tauri/src/commands/infrastructure/dev_tools/workspace.rs:472-480`); a queued `persona_executions` row *is* the queue and is re-admitted at boot (`src-tauri/src/engine/execution.rs:530`).
**Verdict: `adapt`.** The mechanisms are already better than exo's — a SQL row with claim columns is a stronger record than a JSON file, and the withheld `Merge` variant is the reversibility law expressed in a type. What is missing is the sentence: three modules each rediscovered the rule, and `CLAUDE.md` does not carry it, so the fourth will rediscover it too.

**1.4 — The self map.**
exo: `exo/SELF.md` is a checked-in navigation guide handed to the model each turn via `EXO_SELF_MAP` (`exo/harness.ts:64`, `:129-131`), and admits its scope — *"intentionally navigational, not a full architecture document"* (`docs/SELF-CONTROL.md:39`).
personas: `context-map.json` (625 KB, 208 contexts across 16 groups) is generated by the context scan, and `commands/infrastructure/context_map_export.rs::render_section` re-splices a marker-delimited block into `CLAUDE.md` on every scan with everything outside the markers preserved verbatim.
**Verdict: `keep ours`.** A map derived from the tree and refreshed by the scan cannot go stale the way a hand-written one does, and the marker splice means the human's own `CLAUDE.md` prose survives regeneration — which is the harder half and the one exo does not attempt.

## 2. Restart, drain, and stopping work

**2.1 — Restart that outlives its requester.**
exo: `queueRebuildAndRestart` writes the outcome JSON atomically first (`exo/tools/guardian-tools.ts:81-118`), then spawns a `detached`, `unref`'d child with a delay and returns `{updateId, status:"queued", deferred:true, pid, delaySeconds, outcomePath}` **mid-turn** (`:121-159`), so the model can announce the reboot before it happens.
personas: there is no self-restart at all. No `app.restart()`, no `tauri_plugin_process` relaunch, no detached respawn; the only relaunch is the Tauri updater behind a user click and an install-when-idle deferral (`src/hooks/utility/data/useAutoUpdater.ts:148`, `src/features/shared/chrome/UpdateBanner.tsx:27-32`). The tree records the absence: `.ai/applied.jsonl` — *"A restart policy does not exist: personas never auto-restarts, so the amendment's central object has no seam yet"*, with a return condition of "when an auto-restart lands".
**Verdict: `different forces`.** exo restarts because it rebuilds itself from a tree it mounted read-write; personas' code changes arrive as a signed update the operator accepts. There is no seam here and building one would create the risk exo's design exists to manage.

**2.2 — The accepted restart direction, and the half that is missing on both sides.**
personas: `restart-class-recovery` landed 4 of 5 parts on `ef6f8382a` — `classify_stale_executions` replacing the blind sweep (`src-tauri/src/engine/execution.rs:530`, called from `src-tauri/src/boot/recovery.rs:70`); the third value as a nullable `recovery_state` column rather than a widened `ExecutionState`, which was the direction's own stated fallback (`src-tauri/db/src/repos/execution/restart_recovery.rs:74-79`, migration `e17_restart_recovery.rs:37-80`); the mark cleared on **success, not attempt** (`restart_recovery.rs:259-270`, cleared only on `completed` at `executions.rs:1048-1049`, pinned at `restart_recovery.rs:610`); `MAX_CONSECUTIVE_RESTARTS = 3` checked *before* the freshness window (`:70`, `:124`); and a clean-shutdown marker written last on exit and consumed exactly once (`src-tauri/core/src/shutdown_marker.rs:41`, `:72-90`; written at `src-tauri/src/lib.rs:2189-2191`, taken at `boot/recovery.rs:63`). Missing: **the user surface.** `list_unresolved_recoveries` (`restart_recovery.rs:297`) has zero non-test callers; `recovery_state`, `unproven` and `restart_count` appear nowhere under `src/`.
exo: the analogue is the reboot announcement. The guardian writes `.exo/exo-reboot-notice.json`; the fresh adapter runner claims it (`crates/executor/src/adapter/runtime.rs:161-170`) and sends one wakeup per adapter conversation so the agent can announce its return, with notices older than 15 minutes discarded (`docs/SELF-CONTROL.md:47`).
**Verdict: `adopt` — narrowly, and it is the announcement, not the notice.** exo's restart is legible to a human because the agent posts on the way down and on the way back; personas' `unproven` rows are legible to nothing. Both halves of the recovery are worthless without a reader, and the reader is what is missing.

**2.3 — Drain by marker, claimed by unlink, with two deadlines — against kill-first.**
exo: the guardian writes `.exo/exo-adapters.restart`; the runner claims it with `std::fs::remove_file(marker).is_ok()` (`crates/executor/src/adapter/runtime.rs:154-159`) — the unlink **is** the claim, so exactly one claimant wins with no lock. Two deadlines follow: `DRAIN_CLAIM_SECONDS=15` and `DRAIN_GRACE_SECONDS=300` (`exo/scripts/exo-service-guardian:128-129`), and only then `terminate_process_tree` = TERM, sleep 1, KILL (`:195-200`). The whole ladder is `:291-338`, with the rationale in a comment: *"A runner that never claims the marker (an old build, or one wedged mid-task) gets the process tree treatment instead."*
personas: the order is inverted. `cancel_execution` sets the cancel flag (`src-tauri/src/engine/execution.rs:1140-1142`), persists `Cancelled` (`:1147-1155`), **kills the tree immediately** — with the reason stated at the call, *"Kill the child OS process to stop API credit consumption"* (`:1157-1161`) — and only *then* gives the tokio task 5 seconds to write metrics (`:1163-1165`), re-killing anything spawned during the grace (`:1178-1185`). `kill_process` (`:1598`) is `taskkill /F /T` or `kill -9`; there is no signal escalation anywhere on this path.
**Verdict: `adapt`.** The credit argument genuinely justifies killing the *model* fast, and it is a force exo's drain does not face as sharply — exo's in-flight work is a wakeup turn, not a metered vendor session. But it does not justify killing before the child has flushed its own `result` line, and the current shape makes that explicit: the 5-second grace waits for a task whose only data source is already dead. §6.1 shows the `result` line is the *sole* origin of a run's cost. A marker the child could claim before the kill costs one round trip and recovers the number.

**2.4 — Where the two-stage shape already exists in personas.**
personas: build sessions have it — `CLI_EXIT_GRACE_TIMEOUT = 120s` waits for exit *after* stdout EOF and only then kills (`src-tauri/src/engine/build_session/runner.rs:91`, used at `:883`, kill arm `:890-908`), alongside a `CLI_SILENCE_KILL_TIMEOUT = 600s` silence watchdog (`:81`).
exo: the same shape at 15/300 (`exo/scripts/exo-service-guardian:128-129`).
**Verdict: `keep ours`.** The pattern is in the tree, with a longer post-EOF grace than exo's one second between TERM and KILL, and it is attached to the surface where the output actually matters. §2.3 is asking for it to reach `cancel_execution`, not for it to be invented.

**2.5 — Lease versus lock.**
exo: pid files (`.exo/exo-adapters.pid`) with liveness by `kill -0` on the stored pid (`exo/scripts/exo-service-guardian:202-209`).
personas: `daemon.lock` is a heartbeat lease — atomically claimed with `OpenOptions::create_new(true)` (`src-tauri/src/daemon/lock.rs:215`), `STALE_THRESHOLD = 90s` and `HEARTBEAT_INTERVAL = 30s` (`:57`, `:60`), stale takeover deletes and retries (`:184-195`) — and the PID is recorded but **explicitly not used for liveness** (`:30-32`), with `flock`/`LockFileEx` deliberately rejected (`:33-35`). `engine-leader.lock` generalizes the same lease (`src-tauri/src/engine/leadership.rs:53`).
**Verdict: `keep ours`.** A heartbeat lease survives PID recycling and a hard power cut; `kill -0` on a stored pid survives neither. personas' one PID-liveness check in the tree is guarded by `pid_is_node` for exactly this reason (`src-tauri/src/webbuild/devserver.rs:267`) — the tree already wrote down why exo's default is wrong.

**2.6 — Supervision that never respawns.**
exo: the guardian is a real supervisor — it builds, restarts and drains services — and the adapter runtime starts one supervision task per adapter and reconnects after failures with a short delay (`exo/docs/design/adapter-architecture.md:290-300`).
personas: nothing respawns. `freeze_monitor.rs:67` polls RSS every 10s, alerts on >100 MB growth (`:94`) and never acts; `background_job.rs:80` `spawn_guarded` is a panic *boundary* whose doc states the task is not restarted (`:75-79`); the fleet boot sweep deliberately **parks** orphans with a human-readable reason and refuses to auto-kill-and-resume (`src-tauri/src/commands/fleet/persist.rs:265-304`), leaving the kill-then-respawn to an operator-invoked command (`commands/fleet/process_scan.rs:153-178`).
**Verdict: `different forces`.** exo supervises processes it owns and just rebuilt; personas' children are vendor CLIs holding a paid, possibly half-finished session on the operator's own machine, and the tree already argued that auto-resume is the wrong default there. Recorded so a future watchdog does not read exo's supervisor as a target shape.

## 3. Tool and extension surface

**3.1 — Agent-installed code, and which process it lands in.**
exo: `ToolManifest { schemaVersion, id, module }` — three fields, no privilege vocabulary at all (`exoharness/typescript/harness/tool-registry.ts:29-33`) — and `loadToolModule` `import()`s the path straight into the harness process (`exoharness/typescript/harness/tool-modules.ts:200-218`), requiring exactly one exported tool (`:221-241`).
personas: the closest parallel is *not* the "Plugin Ecosystem" group in `CLAUDE.md:17` — those 26 contexts are in-tree React folders and Rust modules, toggled rather than installed (`src-tauri/src/commands/companion/plugins.rs:21`), with no `libloading`, `wasmtime`, `extism` or JS VM anywhere in the workspace manifests. It is the bridge manifest: `BridgeManifest { id, label, binary, actions }` (`src-tauri/engine/src/bridge_manifest/mod.rs:34`), re-globbed from `scripts/bridges/` on every IPC call (`:142`) and dispatched as a child process (`:278-298`), bounded by a 30s timeout (`:30`) and a 50 KiB output cap (`:28`). `parse_manifest_str` (`:85-136`) validates ids, unique action names, param types and `$param` references — and nothing about privilege.
**Verdict: `keep ours`.** The manifests are equally silent about privilege; the blast radius is not. exo evaluates agent-authored TypeScript inside the process that holds its secrets and its event log; personas spawns a binary in a child process it can kill. A process boundary is the whole distinction, and personas has it by accident of being a wrapper rather than by design — which is worth noticing before someone proposes an in-process plugin host.

**3.2 — The privilege model that exists, is tested, and is not wired to one of two doors.**
exo: nothing to reach for.
personas: `DesktopCapability` (`src-tauri/engine/src/desktop_security.rs:22-39`, risk tiers `:57-63`) with `DesktopConnectorManifest { capabilities, allowed_binaries, allowed_paths, allowed_ports }` (`:71`) and a real call-time `check_permission` that verifies the manifest declares the capability *and* the user approved it, returning `AppError::Forbidden` (`:587`), plus `is_binary_allowed` canonicalizing through `PATH` (`:107-124`), `is_path_allowed` with deny-on-empty (`:172-177`) and `is_port_allowed` (`:259`). It has exactly **one** enforcing call site — `src-tauri/src/commands/credentials/desktop_bridges.rs:31-37` — and its manifest-driven sibling `bridge_manifest_dispatch` (`src-tauri/src/commands/infrastructure/bridge_manifest.rs:104-120`) calls `require_auth_sync` and then `dispatch`, reaching neither `check_permission` nor `is_binary_allowed`.
**Verdict: `adopt`.** The cheapest real finding in the study, and it does not come from exo — exo's only contribution is to show what the unguarded door looks like when the code runs *inside* you. Two sibling commands reach the same spawn primitive; one is gated by a tested capability model and the other is not.

**3.3 — Where installed code may come from.**
exo: containment is realpath-based and careful. A local source must resolve inside `realpath(process.cwd())` with the error naming the correct shape (`tool-registry.ts:288-311`); a git source is cloned `--no-checkout`, checked out `--detach` at the pinned commit, and `rev-parse HEAD` is compared to it — *"git checkout did not resolve to the pinned commit"* (`:322-336`); the manifest module is `assertContainedFile`'d by realpath against the staged root (`:534-551`).
personas: the equivalent discipline is `classify_skill_entry` — entry type from `DirEntry::file_type` (which does not traverse), symlinks and Windows junctions rejected, `MAX_SKILL_DIR_DEPTH = 8` — shipped after a measured incident in which `.claude/skills/<name>/refs -> ~/.ssh` was read into the shareable export bundle and **copied into the shared skill library on adopt**, with a self-referential link recursing to stack overflow (`.claude/codebase-stack.md:1036-1056`, commit `ee97789bc`). The copy walk and the hash walk are required to apply identical skip rules, held by a unit test.
**Verdict: `adapt`.** personas checks every entry of the walk by file type; exo realpaths only the entry *module* and copies the source tree with `fs.cp(..., {recursive: true})` (`tool-registry.ts:315`), so a symlink among the sibling files that module later imports is not covered. The transferable half runs the other way: **pin the source commit and verify the checkout resolved to it** (`:332-335`). personas' skill install has no source pinning, and its divergence detection is a hash of what it copied, not of what it was promised.

**3.4 — When the registry is rebuilt.**
exo: `createToolRegistry(context)` is called **inside** the round loop (`exoharness/typescript/model-runtime/turn-loop.ts:112-126`), so a tool installed during round *N* is callable in round *N+1* without ending the turn.
personas: there is no round loop to rebuild in (§4.1). Three registries exist and none is per-round: a hardcoded `Vec<Value>` rebuilt per `tools/list` JSON-RPC request (`src-tauri/src/mcp_server/tools.rs:747`, called at `mcp_server/mod.rs:85-86`); an outbound MCP list cached 60 seconds per credential (`src-tauri/src/engine/mcp_tools.rs:41`, `:569`); and a compile-time `const &[&str]` for Athena (`src-tauri/src/companion/dispatcher/catalog.rs:11`).
**Verdict: `different forces`.** The child CLI owns the round, so no placement of the rebuild can make a tool live mid-turn. Recorded because the per-request rebuild at `mcp_server/tools.rs:747` already gives the equivalent property for anything the CLI chooses to re-list — the property exists, it just cannot be *guaranteed* from this side.

**3.5 — The declared-but-unenforced policy object, on both sides.**
exo: the tool manifest declares nothing to enforce (§3.1).
personas: `EnclavePolicy` (`src-tauri/engine/src/enclave.rs:29`) declares `max_cost_usd`, `max_turns`, `allowed_tools`, `allowed_domains`, `required_capabilities` and `allow_persistence` inside an Ed25519-signed ZIP — and only `seal` (`:127`) and `verify` (`:209`) exist. There is no import, install or execute path; the only commands are `seal_enclave`/`verify_enclave` (`src-tauri/src/lib.rs:2024-2026`), and `allowed_tools` is referenced nowhere but its own declaration and `Default`.
**Verdict: `keep ours` — as a record, not as praise.** Neither tree enforces its manifest; personas' at least is signed and unreachable rather than unsigned and live. Filed here so the next reader does not score `EnclavePolicy` as a control, per the tree's own rule: *"Never score a gated feature as live"* (`.claude/codebase-stack.md:880-882`).

**3.6 — Progressive disclosure as a third extension surface.**
exo: skills are agent artifacts (`skills/index.json` + `skills/<name>.json`) and `skillsInstruction` injects **only name and description** each turn while `use_skill` loads the body and `read_skill_file` the bundled files (`exoharness/typescript/harness/skill-tools.ts:18-19`), with caps at 64 name chars, 1024 description chars, 100k `SKILL.md` chars, 200k per file and 64 files (`:27-32`) and a reserved-name guard so a skill called `index` cannot shadow the catalogue (`:24-26`).
personas: the skills sidecar writes per-connector `SKILL.md` files into the exec dir (`src-tauri/src/engine/runner/mod.rs:792-796`) and lets the child CLI's own loader do the disclosure; personas never injects a skill body itself.
**Verdict: `keep ours`.** Delegating disclosure to the CLI that owns the context window is the correct move for a wrapper, and it yields the same progressive shape without personas owning the budget. The interesting half of exo's design is not the mechanism but its inconsistency with exo's own memory store, which is §5.2.

## 4. Turn control and result size

**4.1 — Who owns the loop.**
exo: twice over — `runResponsesTurnLoop` (`exoharness/typescript/model-runtime/turn-loop.ts:101-140`) and a warm Codex app-server session cached across turns with a per-turn scope swapped onto it (`exoharness/examples/typescript/codex-harness.ts:139`, `:164-180`), logging every JSON-RPC message in both directions (`exoharness/typescript/codex/app-server.ts:320-327`).
personas: none. A linear four-stage pipeline — Validate, SpawnEngine, StreamOutput, FinalizeStatus (`src-tauri/src/engine/runner/mod.rs:114`, stages at `runner/stages.rs:8`) — around a stdout line-read loop (`runner/mod.rs:2365`, `match &line_type` at `:2440`). `max_turns` is a persona config field forwarded verbatim to the child (`src-tauri/engine/src/prompt/cli_args.rs:140-144`); personas never counts turns itself.
**Verdict: `different forces`.** The governing asymmetry, restated where it bites. Every point below reads as "improve the wrapper", never "improve the loop".

**4.2 — What bounds a turn.**
exo: `maxToolRoundTrips` defaults to `null` = unbounded (`exoharness/typescript/harness/index.ts:39`; `max_tool_round_trips: None` on agent creation at `crates/cli/src/main.rs:1319`), and there is **no** wall-clock deadline, abort signal or timeout anywhere in the turn loop.
personas: bounded three ways — `DEFAULT_EXECUTION_TIMEOUT_MS = 660_000` (`src-tauri/src/engine/runner/mod.rs:62`) under a non-overridable `ENGINE_MAX_EXECUTION_SECS = 20*60` (`src-tauri/core/src/limits.rs:15`) enforced at `engine/execution.rs:41` with an orphan-tree kill at `:195`, plus `--max-turns` handed to the child.
**Verdict: `keep ours`.** A wrapper must bound by wall clock because it cannot count the child's rounds — and exo's unbounded default is the weaker choice even for an in-process loop, because nothing stops a tool that always asks for one more round. Combined with §6.5 (no spend guard) this is one omission, not two.

**4.3 — Progress as a bound, not a count.**
personas: `src-tauri/src/engine/deliberation.rs` bounds by progress — `STALL_LIMIT = 3` (`:32`), `MAX_TURNS_PER_TICK = 3` (`:36`, described as *"THE mechanism that makes a turn-budget-free deliberation safe"*), `CONVERGE_BY_ROUND = 12` (`:44`), and an unparseable round counts as a stall (`:53`).
exo: nothing measures progress; the only bound is the round count that defaults off.
**Verdict: `keep ours` — inverse list.** A stall counter measures the thing a round counter proxies for. This was the headline of the hermes study; exo is the second agent-harness peer in a row with no counterpart.

**4.4 — Tool results: artifact first, inline second.**
exo: `compactToolResult` writes the **full** result to `tool-results/<toolName>/<toolCallId>/result.json` before deciding anything, splits `stdout` and `stderr` into their own artifacts, inlines the value only under `TOOL_RESULT_INLINE_LIMIT_CHARS = 8_000`, and returns `{truncated, preview (4_000 chars), resultArtifact, artifacts}` (`exoharness/typescript/harness/tools.ts:14-15`, `:169-235`). The prompt stays bounded and the full output survives.
personas: every path is a cap with a flag and nothing is spilled. `DIRECT_TOOL_OUTPUT_CAP_BYTES = 256 KiB` with the rule stated — *"Truncation is always surfaced via a `truncated` flag — never silent"* (`src-tauri/engine/src/tool_outcome.rs:28-29`); `MAX_OUTPUT_BYTES = 10 MiB` and `MAX_STDERR_BYTES = 100 KiB` on the runner (`runner/mod.rs:2200`, `:2207`); `MAX_TOOL_RESULT_DISPLAY = 200` chars in the stream (`src-tauri/engine/src/parser.rs:6`); `ToolCallStep.output_preview` 500 chars, char-boundary safe (`runner/mod.rs:2663-2667`).
**Verdict: `adopt`.** The flag discipline is personas' and is better stated than exo's. What is missing is the other half: **the full output has no home.** After a run, a 300 KiB tool result exists only inside the child CLI's own transcript — which personas mines for dormancy and nothing else (`.claude/codebase-stack.md:1019`) — while the audit row keeps 500 characters. The `exec_dir` already exists, is already written to by three sidecars, and is already scrubbed on exit; the artifact write is the small half of exo's design and the valuable one.

## 5. Durable state and memory

**5.1 — Always-inject versus retrieve, and which tree is ahead.**
exo: whole-store injection, with the rejection written down — *"This is deliberately not embedding-based retrieval. For a small set of short facts, always injecting the whole store is simpler and easier to audit"* (`docs/SELF-CONTROL.md:89`). Caps `MAX_ENTRIES = 200` and `MAX_TEXT_CHARS = 600` (`exo/tools/memory-tools.ts:21-22`); entries are injected in insertion order, oldest-first, with no ranking of any kind (`:121`, `:127`, render at `:214-217`).
personas: a three-stage retrieval funnel. A tier- and scope-scoped SQL candidate fetch with a decay-aware ranking, where `core` is always in and `archive` never enters (`src-tauri/db/src/repos/core/memories.rs:1867`, `:1893-1897`); a decay-scored greedy pack with category half-lives (`src-tauri/db/src/memory_recall.rs:204`, `:118`, `:157`); and on `ml` builds an embedding blend over a vec0 side table where relevance can only **promote**, never demote (`memory_recall.rs:283`, `:359`). Access counters are incremented for injected memories only, not candidates, so the decay signal is not corrupted by the recall (`runner/mod.rs:1071-1079`).
**Verdict: `keep ours` — inverse list.** exo's own sentence names the condition its choice needs — *"a small set of short facts"* — and its own cap is 200 entries at 600 characters, which is up to 120 KB of unranked prose in every prompt of every conversation. personas crossed that line and built the machinery on the other side.

**5.2 — Why exo's own tree argues against 5.1.**
exo: skills — the *other* agent-writable store, in the same harness, assembled by the same function — inject only name and description each turn and load bodies on demand (`exoharness/typescript/harness/skill-tools.ts:18-19`), while memory injects everything, and both are pushed from the same `exoInstructions` list eight lines apart (`exo/harness.ts:140-151`). Two stores, one harness, opposite disclosure policies, and only the whole-store one carries a design note defending its choice.
personas: both projecting surfaces share one constant — `ACTIVE_MEM_BUDGET_CHARS = 6000` (`memory_recall.rs:196`) — after the `CLAUDE.md` projection was found on 2026-08-12 to have skipped the budget entirely and could show materially more than the system prompt it mirrors (`memory_recall.rs:187-195`, `.claude/codebase-stack.md:902-912`).
**Verdict: `keep ours`.** One budget shared by every surface that projects the same material is the invariant, and personas already paid for the lesson. exo has two disclosure policies for two agent-writable stores and no shared constant to notice it.

**5.3 — Skip, truncate, or reject at the budget edge.**
personas: `pack_by_budget` **skips** an over-budget entry and keeps packing so smaller ones still fit, always admits at least one, and states the rule — *"Entries that don't fit are skipped rather than truncated — a partial memory is worse than none"* (`memory_recall.rs:199-203`, loop at `:218-225`). The loss is counted in the return type, `PackedRecall { selected, omitted }` (`:182-185`), and rendered as an explicit line in the prompt (`runner/mod.rs:1054-1059`).
exo: `remember` **rejects** an over-600-char fact at the door — *"text exceeds 600 characters; summarize it first"* (`memory-tools.ts:114-118`) — which is the same rule, better placed. The row cap then silently `slice(-200)`s the oldest and reports `dropped` only in the tool result (`:125-131`). On the Codex path exo does both and counts both: `CODEX_PRIOR_HISTORY_MAX_CHARS = 24_000` drops whole messages while `CODEX_PRIOR_MESSAGE_MAX_CHARS = 8_000` and `CODEX_PRIOR_TOOL_RESULT_MAX_CHARS = 4_000` truncate within one, and `dropped_message_count` / `truncated_message_count` are emitted as telemetry (`codex-harness.ts:59-61`, `:286-287`, `:904-924`).
**Verdict: `adapt` — two halves, both real.** First, the write-door reject: personas has **no per-entry cap on the write path at all**. `memories::create` validates only non-empty title and content (`memories.rs:362-367`) and clamps importance (`src-tauri/src/engine/dispatch.rs:730`); `MAX_MEMORY_CONTENT_LEN = 50_000` exists but gates import/export validation only (`src-tauri/src/commands/core/export_types.rs:19`). A 40 KB "fact" can be written and will then be silently skipped by the packer forever. Second, the counted loss: `omitted` lives in the struct and the prompt line and is aggregated nowhere, so nobody knows how often the budget bites.

**5.4 — Compare-and-swap, and the same hole in both trees.**
exo: the event log **has** CAS. `append_events_to_conversation` takes an `expected_head` and `ensure_conversation_head` rejects a mismatch (`crates/exoharness/src/basic.rs:4475-4482`, `:4516-4532`), and `ConversationHeadMismatch` (`:4534`) is the **only named struct error** in a workspace of 462 `bail!`s. The memory store has none, and the TODO says so in full: *"remember/forget are read-modify-write with no compare-and-swap. Agent-scoped memory is shared across conversations, so two channels running turns concurrently can both read version N and both write N+1, losing one update"* (`exo/tools/memory-tools.ts:71-76`).
personas: the identical shape one layer over. `memories::create` is check-then-act — `find_normalized_duplicate` SELECT at `src-tauri/db/src/repos/core/memories.rs:401`, unguarded INSERT at `:420` — with no transaction and no UNIQUE index on `(persona_id, content)`; every index on `persona_memories` is non-unique (`src-tauri/db/src/migrations/schema.rs:537-541`). Two concurrent executions emitting the same fact both miss the duplicate and both insert. The JSON-blob-in-`app_settings` stores lose whole updates the same way: `src-tauri/src/engine/digest.rs:26`→`:37`, `src-tauri/db/src/quality_gate.rs:145`→`:164`, `src-tauri/engine/src/app_master.rs:854`→`:898`.
**Verdict: `adopt` — and this is the study's sharpest point, because it is symmetric.** **Both trees built the correct primitive and then did not use it for memory.** exo has `expected_head`. personas has three: optimistic versioning — `UPDATE … WHERE id = ? AND trigger_version = ?` with a race test (`src-tauri/db/src/repos/resources/triggers/scheduling.rs:265-275`, `triggers/cross_domain_tests.rs:1520`); `BEGIN IMMEDIATE` for the read-max-then-insert pattern (`repos/resources/recipes.rs:500`, `teams.rs:379`, `research_lab.rs:159`); and a per-key async mutex whose doc comment describes exactly this failure mode (`src-tauri/engine/src/oauth_refresh_lock.rs:1-40`). Neither tree faces a design question here. Both face an application.

**5.5 — Two postures on a damaged store.**
exo: the write path throws on a corrupt memory artifact so nothing overwrites it, and the read path degrades to a developer note telling the model memory is unavailable rather than pretending it is empty (`memory-tools.ts:44-69`, `:190-218`), pinned by a paired test — one asserting `remember` rejects, one asserting `memoryInstruction` returns the note (`memory-tools.test.ts:150-172`).
personas: the same idea, one abstraction level down and considerably further. `src-tauri/db/src/damage.rs` splits by **damage class on the extended result code**, not by caller: `SQLITE_CORRUPT_VTAB` (267) is derived, bare `SQLITE_CORRUPT`/`SQLITE_NOTADB` canonical (`:132-151`), with *"No branch here reads the error text"* (`:38-45`). Derived damage detaches the FTS triggers in one transaction, writes a durable stale marker, and the canonical write is retried once and succeeds (`:308-326`, `:368-372`); canonical damage quarantines and refuses every write at the **engine** — `PRAGMA query_only` plus `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE` on every pool acquire (`:242-264`, `src-tauri/db/src/lib.rs:258-260`) — while keeping reads available deliberately, because quarantine must be a state you can read and export out of (`:254-256`). Three tests including a positive control (`:483`, `:561`, `:620`).
**Verdict: `keep ours`.** The class axis subsumes exo's read/write axis. exo asks *who is calling*; personas asks *what is broken*, and only the second can decide that a rebuildable index should degrade while a corrupt page should stop everything. The paired-test discipline is identical on both sides and personas additionally carries the control.

**5.6 — The degraded read that was promised and stopped one call short.**
personas: `damage.rs:305-307` promises the stale marker is *"readable through `repos::core::settings::get`, so a search surface can label a degraded answer as degraded instead of quietly returning fewer rows"* — and `fts_detached` (`:329`) has **zero production callers**; its only other references are two test assertions (`:522`, `:627`). Today a derived-damage detach silently returns fewer execution-search rows and no surface says so. The `escape_like` helper the store-damage direction pointed at exists (`memories.rs:43`) and is not wired to the marker.
exo: `memoryInstruction` catches, logs loudly, and returns the degraded note; the note *is* the surface (`memory-tools.ts:203-208`). There is nothing left to wire.
**Verdict: `adopt`.** A one-line pattern personas already argued for, in its own module comment, and did not finish. The degradation is invisible precisely where it matters — an operator searching executions after a corruption event sees a shorter list, not a warning.

## 6. Cost attribution

**6.1 — Self-reported, never re-stamped, on both sides — for different reasons.**
exo: `response.provider_cost_usd.or_else(|| pricing.compute_cost_usd(...))` (`crates/executor/src/basic.rs:541-556`), stamped once into a `UsageRecord`. Nothing recomputes it: `recompute` / `backfill` / `restamp` return no hits across `crates/`, `exoharness/typescript/` and `exo/`.
personas: the dollar comes verbatim off the CLI's terminal `result` event — `total_cost_usd` at `src-tauri/engine/src/parser.rs:357`, assigned without arithmetic at `:866-868`, persisted by `cost_usd = COALESCE(?9, cost_usd)` (`src-tauri/db/src/repos/execution/executions.rs:1027`), with two further ledgers (`dev_llm_spend` at `src-tauri/db/src/repos/llm_spend.rs:44-66`; `companion_turn` at `src-tauri/src/companion/turn_ledger.rs:320`). No re-stamp, no `verified_at` on any price row, and every read is a live `SUM(cost_usd)` re-aggregation (`executions.rs:1926`).
**Verdict: `keep ours`.** For a wrapper the vendor's figure is authoritative — it is computed from the billing system that will actually charge — and re-deriving it would be strictly worse. Recorded because the reasons differ and only one is safe: personas trusts a number its provider computed; exo trusts a number it computed itself from a table it fetched over the network.

**6.2 — The price table, and the one place exo is clearly ahead.**
exo: `crates/cost/src/loader.rs` fetches LiteLLM's published `model_prices_and_context_window.json` with a 24-hour TTL and a stated degradation ladder — *"explicit path -> fresh cache -> fetch (cached on success) -> stale cache -> empty. Never fails: any error…"* (`:1-2`, `:12`) — logging distinctly at each rung (`:47`, `:52`, `:56`, `:66`). The table carries `cache_read_input_token_cost` and `cache_creation_input_token_cost` per model (`exoharness/typescript/model-runtime/cost.ts:12-13`) and lookup falls back to the longest key that is a prefix at a token boundary (`:36-56`).
personas: three independent hardcoded tables and none of them is the run's cost. `src-tauri/engine/src/cost.rs:15-60` is substring-matched family pricing whose `else` branch silently defaults an unknown model to Sonnet-class 3.0/15.0 (`:32`, `:57`), used only for the pre-flight preview. `src-tauri/src/engine/http_engine/config.rs:33-39` has two Qwen models and stamps `0.0` for anything else (`:32`, `openai.rs:228-233`). `src/lib/utils/platform/pricing.ts:6-28` is 17 display-only keys. None has cache tiers; none has a verification date.
**Verdict: `adopt`.** personas' own golden path already wrote the fix as prose with zero code behind it — *"one table, one type — `struct ModelPrice { input_per_m, output_per_m, cache_read_per_m, cache_write_per_m, verified_at: &'static str }` … and a compile-time or CI assertion that `verified_at` is under N months old. Delete the `else` fall-through in `cost.rs`"* (`docs/concepts/golden-paths/llm-spend-accounting.md:652-655`); `ModelPrice` returns zero hits in any `.rs` or `.ts` file. exo supplies the half the prose does not: a maintained external source and a loader whose failure modes are enumerated and none of which is an exception.

**6.3 — The two cache buckets, and a real undercount in the peer.**
exo: the Rust path parses, stores, prices **and tests** both buckets (`crates/executor/src/basic.rs:527-534`, `:550`; `harness_basic_tests.rs:363`, `:431` assert 2,000 cache-creation tokens survive). The TypeScript port — self-described as *"a self-contained port of the `cost` crate's math and loader"* (`cost.ts:1-3`) — accepts `cacheCreation` in `TokenCounts` and prices it at `cache_creation_input_token_cost` (`:22`, `:70`, `:76`), and its **only call site never passes it**: `usageRecord` builds `{prompt, completion, cached}` (`responses.ts:1181-1183`) from an adapter that reads `cache_read_input_tokens` and nothing else (`:698`). Because `isAdditive("anthropic")` is true (`cost.ts:85-91`), `prompt` is Anthropic's `input_tokens`, which *excludes* cache-creation tokens — so on the Anthropic path cache writes are priced at **zero**, not at 1.25×. No TypeScript file other than `responses.ts` mentions `cost_usd`.
personas: both buckets are parsed with unusual care — `cache_creation_input_tokens` is read from `usage`, then top-level, then summed from the nested ephemeral 5m/1h breakdown per CLI 2.1.152 (`src-tauri/engine/src/parser.rs:369-388`) — accumulated (`:875-880`), persisted (`runner/mod.rs:3187-3192`), bound to TS (`src/lib/bindings/PersonaExecution.ts:14`, `:18`) and displayed (`inspectorShared.tsx:34-35`). Neither is ever priced: `estimateCost` takes only `(model, inputTokens, outputTokens)` (`src/lib/utils/platform/pricing.ts:49-53`), and `dev_llm_spend`'s dashboard totals SUM the read bucket and omit the creation one (`llm_spend.rs:150`, `src/lib/bindings/LlmSpendTotals.ts:3`).
**Verdict: `keep ours` — with the reason inverted from the seed.** personas stores both and prices neither, which is a *display* gap sitting behind an authoritative vendor total. exo prices one and drops the other, which is a *wrong number* in the only total it has. And the cause is instructive: exo deliberately duplicated one policy across two languages, and the copy without a test drifted in the direction that loses money.

**6.4 — Tests that assert a persisted cost.**
personas: five, all round-tripping through SQLite — `(completed.cost_usd - 0.005).abs() < f64::EPSILON` after an `update_status`/`get_by_id` cycle (`executions.rs:2692`); a six-row monthly rollup asserting `1.75` that pins the exclusion semantics in the same test (`:3186`); the companion ledger re-`SELECT`ing `0.42` (`turn_ledger.rs:538-544`); `policy_evidence.rs:209`; chain propagation at `executions.rs:2878`.
exo: zero.
**Verdict: `keep ours` — inverse list, and it is the direct cause of §6.3.** exo's Rust cost path has a test asserting cache-creation tokens survive; its TypeScript path has none; only the untested one is wrong. Two implementations of one policy is a drift surface, and a test on one arm is not a test on the other.

**6.5 — Budgets that bite.**
personas: four guards, two of which stop a run before it starts. A hard per-persona monthly cap returning `AppError::Validation` (`src-tauri/src/commands/execution/executions.rs:376-389`), sharing one `MONTHLY_SPEND_PREDICATE` with the UI feed so the gate and the display cannot disagree (`db/src/repos/execution/executions.rs:1899-1913`); a scheduler pre-check (`schedule_over_budget`, `src-tauri/src/engine/background/scheduler.rs:286`); an admission refusal `AttentionRefusal::BudgetExhausted { spent_usd, limit_usd }` (`src-tauri/core/src/cycle.rs:192-194`); and the aggregate `run_budget.rs` ceiling, which is warn-only unless `PERSONAS_RUN_BUDGET_ENFORCE` is set (`:20-27`, `:83-86`) though two consumers hard-stop off `is_exceeded` regardless (`engine/evolution.rs:443-450`, `engine/fitness_driver.rs:280-284`).
exo: none. There is no `max_cost_usd` anywhere; the only bound on spend is the round cap that defaults to unbounded (§4.2).
**Verdict: `keep ours` — inverse list.** A harness whose canonical launcher mounts its own tree read-write, whose turn has neither a round nor a wall-clock bound, and which has no spend guard, has one omission expressed three ways. personas' fourth guard being warn-only is worth its own look, but four guards with one soft is not the same class of gap as zero.

## 7. External channels

**7.1 — The seam between host and protocol.**
exo: the host owns supervision, the outbox, inbound dedupe, secret resolution and wakeups; the per-network worker owns protocol only, over one newline-delimited JSON stream with a five-variant event vocabulary and a one-variant command vocabulary (`exo/docs/design/adapter-architecture.md:140-158`; `crates/executor/src/adapter/worker.rs:15-68`). Seven networks — agent-cli, Discord, ExoChat, IRC, Signal, Slack, WhatsApp — share one runtime; adding one is a worker, not a runtime change. The design states the goal: *"This keeps protocol code in Exo while preserving one host-owned supervision, event, wakeup, and outbox implementation in Rust"* (`:157-158`).
personas: five networks, each bespoke and full-stack. `deliver_to_channels` dispatches on `external.channel_type.as_str()` to five hardcoded free functions in one 83 KB file (`src-tauri/src/notifications.rs:483-493`, senders at `:625`, `:710`, `:756`, `:850`, `:920`); adding a network means editing that match, `channel_type_str` (`:1242`) and the `ChannelSpecV2Type` enum (`src-tauri/core/src/models/persona.rs:365-373`). A real trait exists but is unexercised: `EventProcessor` (`src-tauri/src/engine/webhook_notifier.rs:125`) is selected by `processor_for_subscription` (`:139`) which unconditionally returns `Box::new(WebhookProcessor)` (`:140`), with a doc comment saying future kinds will *"add arms here"*. The pollers are the fullest-stack of all: `slack_poller.rs` (55 KB) and `discord_poller.rs` (26 KB) each own their cursor table, rate-limit handling, parsing, reply formatting and HTTP, sharing only transport-agnostic reply extraction (`src-tauri/src/engine/channel_reply.rs:1-13`).
**Verdict: `adapt`.** The seam is right; the worker-process architecture is not — five channels on one desktop do not need five processes. The transferable half is the **inventory**: supervision, queueing, dedupe, secret resolution and retry are host concerns, and today each is duplicated per channel or absent. `EventProcessor` is the declared seam that would carry it and has never had a second arm.

**7.2 — Whether an outbound send is durable.**
exo: `send_adapter_message` writes an outbound event for history and an `AdapterOutboundMessageRecord` into a four-directory state machine — `outbox/` → `inflight/` → `delivered/` or `failed/` (`crates/executor/src/adapter/store.rs:533-563`, transitions `:330-374`) — drained once per second by the runtime, with a boot sweep that requeues everything stranded in `inflight` (`:379-407`). The design names the property this buys: *"The outbox also decouples conversation turns from socket ownership. The model turn can finish after queueing a message"* (`adapter-architecture.md:275-277`).
personas: no send queue exists — no `CREATE TABLE` in `src-tauri/db/src/migrations/` creates one. `notify_*` is fire-and-forget: `tokio::spawn` per channel (`notifications.rs:472`, `:545`), a failure is a `tracing::warn` (`:500`, `:569`) plus an **in-memory** counter that dies with the process (`DELIVERY_METRICS`, `:151`, `:226`, read by `get_notification_delivery_stats` at `:1506`). Webhooks have a **shared** watermark rather than a per-recipient cursor (`webhook_notifier.rs:621`, `:730`; table at `e05_twin_and_memory_review.rs:384`), so retry means holding the global cursor below the earliest failure and **re-sending deliveries that already succeeded** at or after that timestamp, with no idempotency key to protect the receiver — and the code names its own gap: *"A per-(event,subscription) retry cursor remains the deeper fix for per-sub at-least-once replay"* (`:712-713`). Circuit breakers stand in for queues (`webhook_notifier.rs:493-578`; `team_slack_relay.rs:99-163`, five consecutive failures then a probe every 12 ticks).
**Verdict: `adopt` — the strongest channel finding.** personas already carries `delivery-guarantees` as a subject in its applied ledger, and this is the surface with none: a notification that fails while the laptop's Wi-Fi is off is gone, and the only evidence is a counter that resets on restart. exo's four-directory outbox is small, file-backed, and boot-recoverable — the shape a local-first app can actually adopt.

**7.3 — Inbound exactly-once, and a natural key thrown away.**
exo: `record_inbound_message_once` uses `OpenOptions::create_new(true)` on a per-message marker keyed by `stable_message_key(target, message_id)` (`crates/executor/src/adapter/store.rs:475-505`) — the atomic file create **is** the claim — with a test asserting the second call returns false (`:1017-1026`).
personas: the natural key is already there and is then discarded. `slack_inbound_messages` has `PRIMARY KEY (channel_id, message_ts)` (`e05_twin_and_memory_review.rs:610-623`) plus `replied_message_ts` and `error` — but `list_pending_replies` filters `error IS NULL` (`slack_poller.rs:1180-1182`) while `mark_reply_error` writes `error` on **any** failure (`:1218-1230`), so a single transient Slack 5xx drops that reply permanently. No retry, no backoff, no attempt counter. Genuine idempotency keys exist on the execution side only — `channel:{persona_id}:{message_id}` (`src-tauri/src/commands/communication/persona_channel.rs:599`), `create_with_idempotency_reporting` (`commands/execution/executions.rs:401`).
**Verdict: `adapt`.** The dedupe half is already stronger than exo's — a table primary key beats a marker file. What is missing is the distinction between *delivered* and *permanently failed*: an attempt counter and a retryable/terminal split on `error` would reuse `ErrorCategory` (§9.1), which exists and already knows what a transient 5xx is.

**7.4 — Outbound gating by topology, not by a check.**
exo: exactly one production caller of `enqueue_outbound_message` (`crates/executor/src/adapter/runtime.rs:401`), reached from exactly one tool handler (`crates/executor/src/adapter/tools.rs:915`). The property — *"model text is never automatically posted back externally — `send_adapter_message` is always an explicit decision"* (`docs/SELF-CONTROL.md:147`) — is verified by enumerating two edges, not by auditing behaviour.
personas: roughly **14 write sites across 7 modules**. Six reach `deliver_to_channels` (`notifications.rs:1096`, `:1112`, `:1127`, `:1159`; `engine/dispatch.rs:636` bypassing the wrappers; `engine/digest.rs:633`); three reach `deliver_spec_now` (`team_slack_relay.rs:427`, `:491`, `notifications.rs:1441`); and five bypass `notifications.rs` entirely — `webhook_notifier.rs:188`, `slack_poller.rs:773`, `discord_poller.rs:490`, `companion/jobs/connector_use.rs:701`/`:822`, and the widest of all, `engine/tool_runner.rs:689`, a `curl`-backed API tool that can POST to an arbitrary host. Three of these own their own retry policy, breaker and metrics. Echo prevention exists in exactly one place, for one bridge (`slack_bridge.rs:119`, invariant at `:42-44`).
**Verdict: `adopt`, narrowly — one chokepoint, not one writer.** personas already has the harder pieces: an SSRF validator on user-supplied webhook targets (`notifications.rs:615-620`), `SecureString` zeroized after the POST (`:670-699`), and approval gating on the two companion connector sends (`companion/connectors.rs:120`, `:140`). What it does not have is a place those are guaranteed to run, and four agent-output→network paths fire with no human in the loop (`dispatch.rs:512`, `:636`; `slack_poller.rs:773`; the team-channel relay tick).

**7.5 — Where the routing intent lives.**
exo: in a prompt. A scheduled task carries its external destination inside the `reportPrompt` — natural language telling the model to call `send_adapter_message` with a given `adapterId` and `target` and to *"Keep the message under 400 chars"* — and the design admits the coupling: *"Scheduled tasks are generic; they do not know that they were created from IRC unless the agent records that intent"* (`adapter-architecture.md:325-340`). The scheduler and the adapter runtime *"cooperate through the conversation, not by calling each other directly"* (`:301-303`).
personas: routing is typed and tested. `admission_conflict_key` derives from `_event.source_type == "trigger"` and `_event.source_id`, requires `payload.trigger_type == "schedule"` because webhooks have no event identity, and excludes backfill slots (`src-tauri/engine/src/queue.rs:130-156`), with six derivation tests (`:1607-1700`). The channel target is a `ChannelSpecV2` with a typed scope and a validator that rejects an empty use-case list (`src-tauri/core/src/models/persona.rs:365-380`).
**Verdict: `keep ours` — inverse list.** exo's own document names the failure mode and then answers it with a string the model must read correctly every time. personas' equivalent is a column a test asserts on, and the tests exist.

**7.6 — Who holds the secret when the work leaves the process.**
exo: the host resolves secrets and hands the worker **derived environment variables** (`crates/executor/src/adapter/runtime.rs:1047-1061`, `worker_secret_env`), so the worker process does hold plaintext for its own network. The harness is described as *"the minimal infrastructure to protect secrets"* (`docs/RSI.md:44-45`), and macOS Keychain access for background scheduler runs is called out as a real operational hazard (`adapter-architecture.md:342-352`).
personas: a split posture, and the good half is not used where it matters. For messaging channels the host holds the secret and does the send — `resolve_credential_fields` decrypts in-process (`notifications.rs:346`, `:369`) and the `deliver_*` functions make the call, so a bot token never leaves the process. For the wrapped CLI the opposite: `inject_credential` decrypts and pushes every non-skipped field as `{CONNECTOR}_{FIELD}` (`src-tauri/src/engine/runner/credentials.rs:754`, `:917-945`) and `build_and_spawn_core` applies them with `cmd.env` (`src-tauri/engine/src/cli_process.rs:610-612`), guarded only by a name denylist and prefix families (`runner/env.rs:25`, `:71`, `:83`) and a metadata skip list (`credentials.rs:908-915`). Meanwhile a zero-plaintext path exists — `credential_broker.rs:1-23`, revocable handles routed through `/api/proxy/{credential_id}`, default-deny scope intersection at `:8-12`, TTL-clamped derived handles at `:41-46`, enforced at `engine/management_api.rs:830` — **and the persona execution runner does not use it.**
**Verdict: `adapt`.** exo's arrangement is not better; both hand a child plaintext. What transfers is the framing that makes personas' own asymmetry visible: the host-does-the-send posture is already the tree's answer for five channels and the broker is already the tree's answer for external API consumers, and the one consumer holding the most credentials — the spawned CLI running with permission checks disabled (§8.1) — gets neither.

## 8. Sandbox and isolation

**8.1 — Whether the agent's shell runs in a box.**
exo: yes. The shell tool runs inside a Docker container or a Firecracker microVM (`crates/exoharness/src/basic.rs:100-143`), with a typed two-state `SandboxNetworkPolicy` (`crates/exoharness/src/sandbox.rs:75-78`, resolved at `basic.rs:4445-4449`), an idle TTL on the lifecycle (`:4455-4457`), and host-mediated file egress — a `sandboxPath` attachment is copied into `.exo/adapters/media` by the host before it is queued (`adapter-architecture.md:265-272`).
personas: no. Searching `src-tauri/{src,engine,core}` for `seccomp|bubblewrap|firejail|landlock|AppContainer|JobObject|chroot|unshare` finds zero enforcement code; the only hits are string literals in an MCP-config *validator* that rejects agent-authored `docker run --privileged` entries (`src-tauri/src/engine/mcp_tools.rs:1878`, `:1897`, `:2018`). The child inherits the full environment, gets `cmd.current_dir(dir)` (`src-tauri/engine/src/cli_process.rs:598-600`), and `creation_flags(0x08000000)` on Windows is `CREATE_NO_WINDOW` — cosmetic, not a job object (`:593`); `kill_on_drop(true)` (`:594`) is a lifetime guarantee, not a privilege one. Permission checks are disabled on eleven spawn paths (`src-tauri/engine/src/prompt/cli_args.rs:107`, `:296`; `cli_process.rs:423`; `commands/fleet/{pty.rs:372,:416, headless.rs:134, external.rs:169}`; `companion/session/cli.rs:108`; `companion/brain/oneshot.rs:179`; `engine/memory_reflection.rs:340`; `engine/project_tracking/consolidator.rs:444`; `engine/build_session/fix_pass.rs:198`), and the stack doc states the trade — *"sandbox handled at app level via IPC auth"* (`.claude/codebase-stack.md:56`).
**Verdict: `different forces`, with one reservation worth writing down.** personas exists to let an agent act on the operator's own machine and repos; `scope.does` says "one operator per install", and a container would make it a different product. The reservation is that "handled at app level via IPC auth" is a claim about who may *invoke personas*, not about what the child may do once spawned — and two modules in the tree already name the gap precisely, treating *"attacker-chosen `current_dir` under permission-skipping"* as their own threat model (`src-tauri/src/commands/infrastructure/dev_tools_http.rs:20`, `src-tauri/src/local_http/auth.rs:9`). The default working directory makes it concrete: `temp_dir()/personas-workspace/<persona_id>` is stable and reused across executions by design (`runner/mod.rs:738-746`), so two concurrent runs of one persona share a directory whenever worktree isolation is off.

**8.2 — The scope ladder, and the operation it does not cover.**
exo: a turn handle may `snapshot_sandbox` and `start_sandbox` but cannot `create`, `fork`, `restore`, `terminate`, `attach`, `detach` or run a process — because `SnapshotHandle` and `SandboxHandle` are two traits (`crates/exoharness/src/types.rs:39-48`) whose blanket impls are gated on two different markers: `impl<T: BasicSandboxScope> SnapshotHandle` (`basic.rs:1195-1197`) versus `impl<T: BasicFullSandboxScope> SandboxHandle` (`:1210-1212`). `BasicAgentHandle` (`:1615`) and `BasicConversationHandle` (`:3150`) implement the marker; `BasicTurnHandle` implements only `BasicSandboxScope` (`:3748`), so the wider methods **do not exist on it**. A runtime `ensure_full_sandbox_scope` (`:2330-2335`) guards the same seventeen operations a second time for the turn-scoped event sink — belt and braces, with the type as the belt.
personas: there is a ladder, and it is a runtime `u8` comparison. `Mandate` has rungs `RUNG_READ = 0`, `RUNG_RETRY = 1`, `RUNG_BRANCH = 2` with `MAX_GRANTABLE_RUNG` refusing deploy/merge and change-gates at intake (`src-tauri/engine/src/app_master.rs:63-71`), enforced by `permits_rung` — `if required <= self.scope_rung` returning `Result<(), MandateRefusal>` (`:179-189`) — with actions mapped at `src-tauri/engine/src/autonomy.rs:174-203` and exactly two call sites (`:268`, `:283`). A second orthogonal gate, `ForbiddenClass`, is scanned deterministically over a unified diff (`app_master.rs:97-110`, `:174`). The rung lives as data in an `app_settings` JSON row, so the compiler cannot tell a read-only caller from an authoring one; `ReadOnly`/`PhantomData<` return only test names. **And creating or destroying an isolated environment is gated by nothing**: `ExecutionWorkspace::new_for_execution` (`src-tauri/src/commands/infrastructure/dev_tools/workspace.rs:520`) and `prepare_authoring_worktree` (`src-tauri/engine/src/unattended_worktree.rs:228`) take no capability, check no mandate, and return no distinct handle type — `permits_rung`/`required_rung` appear nowhere outside `app_master.rs` and `autonomy.rs`.
**Verdict: `adopt` — the technique, not the sandbox.** exo's ladder is enforced by *which trait is implemented*, so the illegal call is a compile error rather than a check someone forgot. personas has already proved it can express a capability in a type on exactly this kind of surface: `Observer` returns `()` **by signature** so an observer cannot withhold a decision (`src-tauri/src/engine/runner/hooks/mod.rs:141`, `:231-236`). The same move on `DesktopCapability` would make §3.2's skipped gate unrepresentable rather than merely unwritten, and the same move on worktree creation would put the operation exo protects most carefully under the ladder personas already has.

**8.3 — Rewind that is wired, and the variant deliberately withheld.**
exo: `snapshot_sandbox` / `rewind_sandbox` with the boundary stated — *"Rewind does not erase history… it does not roll back conversation events, artifacts, adapter records, scheduler records, or secrets"* — and both record events into the log so a later reader can reconstruct what was rolled back and when (`docs/SELF-CONTROL.md:75-76`). *"Git is the second immutable log"* because the repo mount is host-backed (`:77`).
personas: the same second log, used as the primary one. `execution_worktree_isolation` gives an execution its own worktree at `<temp>/personas-exec-wt-<id>` on branch `personas/exec/<id>` forked from HEAD, with the fork point captured first (`workspace.rs:520-590`, `:543-556`) and a collision refusal (`:561-568`); `finalize(ExecutionIntegration::LeaveAsBranch)` auto-commits dirty work, removes the worktree and keeps the branch for review (`:621-701`). The enum has one variant and the doc says why — *"auto-merging into the user's real base branch would mutate their repo without consent"* (`:472-480`). Gate runs use `git worktree add --detach` so a gate cannot disturb a shared checkout (`:223`), and the unattended lane's isolation is mandatory rather than opt-in, with the incident that caused it written into the header (`unattended_worktree.rs:6-24`).
**Verdict: `keep ours`.** A worktree on a named branch is a snapshot whose rewind is `git checkout`, whose diff a human can read, and whose retention decision is a withheld enum variant rather than a config flag. exo's filesystem snapshot is stronger for the state git does not track and weaker for everything a person needs to review. Recorded, not proposed: the strong form is default-off (`runner/mod.rs:667`, `:680-687`) and silently falls back when the persona has no pinned git project (`:727-732`).

**8.4 — The checkpoint module with zero callers.**
exo: rollback is a documented practice with primitives behind it — `snapshot_sandbox` before a risky experiment, `git revert`/`restore` for code, `rewind_sandbox` for filesystem state, `manage_tool` for installed tools, `disable_adapter` for adapters, *"while the event log preserves the record of what was tried, so the next attempt starts from knowledge rather than amnesia"* (`docs/SELF-CONTROL.md:180-190`).
personas: the primitive is already written and nothing calls it. `src-tauri/engine/src/git_checkpoint.rs` implements `checkpoint_stage` — a commit on `personas/run/<run_id>` with hardened flags (`gc.auto=0`, `commit.gpgsign=false`, `core.hooksPath=/dev/null`, `:19-28`, `:61`) — plus `snapshot_stage` via `git stash create` with its tracked-only limitation documented (`:106-115`), `fork_from_checkpoint` (`:128`) and `rollback_to` (`:138`). Excluding `target/`, the only references in the tree are the `pub mod` declaration (`src-tauri/engine/src/lib.rs:113`) and a doc comment in the table repo (`src-tauri/db/src/repos/dev_run_checkpoints.rs:3`). The `dev_run_checkpoints` table exists and this module never writes it. The header still states the motivating problem in the present tense: *"Personas' dev-tools plugin runs agents in real git repositories with zero checkpointing — a run that goes sideways mid-task has no clean rewind"* (`:3-5`).
**Verdict: `adopt`.** This is the finding with the shortest distance between the code that exists and the capability that does not, and exo's only contribution is to show what the wired version buys: a rollback path that a run's own record points at. The module is hardened, the table is migrated, and the caller is missing.

## 9. Failure records and typed errors

**9.1 — Whether failure has a type.**
exo: `thiserror` is a declared dependency of `crates/exoharness` (`Cargo.toml:76`) and there is not one `#[error(...)]` or `derive(Error)` in the workspace. Failure is `anyhow` and 462 `bail!`s carrying free-form strings. The single exception is `ConversationHeadMismatch` (`crates/exoharness/src/basic.rs:4534`) — typed because a caller has to branch on it and retry.
personas: `ErrorCategory`, 11 variants, `Serialize + TS`, snake_case (`src-tauri/core/src/error_taxonomy.rs:25-57`); `ToolErrorKind` with a stable machine token stored in `tool_execution_audit_log.error_kind` (`src-tauri/engine/src/tool_outcome.rs:31-40`); `DamageClass` on extended result codes (`src-tauri/db/src/damage.rs:76-83`). The `typed-failure-classification` direction landed with the nullable column and no backfill (`migrations/incremental/e18_failure_classification.rs:37-47`), three mint sites (`error_taxonomy.rs:132`, `:152-168`; `runner/mod.rs:3051-3056`) that return `None` rather than guess when a non-zero exit carries stderr (`error_taxonomy.rs:148-164`), a `COALESCE` write that never invents a class (`executions.rs:1035-1039`), a `GROUP BY error_category` fast path with a ladder fallback for null rows (`db/src/repos/execution/metrics.rs:641-673`), and five guard tests including `the_mint_reads_no_message` and `a_diagnostic_exit_mints_nothing_and_falls_back_to_the_ladder` (`error_taxonomy.rs:949-1028`).
**Verdict: `keep ours` — inverse list, decisively.** exo's one typed error proves it knows the technique and applies it exactly where a retry loop forces its hand. personas applies it where a *policy* forces it — retry, backoff, scheduled resume, healing, issue creation — which is the far larger surface and the one where a wrong class costs money.

**9.2 — Whether a failure is a durable record.**
exo: failures are events in the per-conversation log, and the doc names the gap — *"host events currently cover the adapter runner only. The scheduler runner and the control REPL do not yet write start/drain/crash events into the log, and there is no agent-level (cross-conversation) event stream"* (`docs/SELF-CONTROL.md:79`).
personas: three durable artifacts. The `persona_executions` row carrying status, `error_message` and `error_category` in one UPDATE (`executions.rs:1017-1050`); a `persona_healing_issues` row per failed run with severity, category, suggested fix and `UNIQUE(persona_id, execution_id)` (`migrations/schema.rs:547-566`, created at `engine/healing_retry.rs:179-184`); and `scheduled_retries`, the durable retry intent that survives a restart (`migrations/incremental/support.rs:623-635`, repo at `repos/execution/scheduled_retries.rs:39`). Retry is dispatched from the class with per-class backoff — `RateLimit` at `30s << consecutive`, `SessionLimit` to the provider's parsed reset time, `ApiError` to an escalating 10/20/30-minute `RetryAt` that resumes the session, `TransientProcessFailure` to a short fixed delay (`src-tauri/core/src/healing.rs:308-353`, `:147-215`, `:470-501`, `:533-571`), escalating to `CreateIssue` at `MAX_RETRY_COUNT = 3` (`:128`).
**Verdict: `keep ours`.** Three tables against one append-only directory with a stated coverage gap. Recorded with one note so a future column does not get added: retryability is deliberately re-derived from `(category, retry_count, consecutive_failures)` on every read rather than stored, which is correct — a stored retryability would go stale the moment the policy changed.

## Tests to initiate

Paired, with the instrument and the number that would move.

**T1 — Does the cancel path throw away the run's own cost record?** (§2.3, §6.1)
The `result` line carrying `total_cost_usd` is the last thing the child writes, and `kill_process` runs before the 5-second metric grace begins. *Instrument*: `persona_executions.cost_usd` null rate partitioned by terminal status, over the live database. *Number that would move*: share of `Cancelled` rows with a null `cost_usd` — predicted high, target the same rate as `Completed`. *Paired arm*: the `Completed` null rate must not move at all — if it does, a drain marker has delayed a kill that was doing its job, and the credit argument at `execution.rs:1157` wins.

**T2 — Does memory dedup actually dedup under concurrency?** (§5.4)
Admit two executions for one persona that emit the identical `agent_memory` payload, with `max_concurrent = 2`. *Instrument*: row count in `persona_memories` for that `(persona_id, normalized content)`, and whether `find_normalized_duplicate` (`memories.rs:401`) returns a hit on the second insert. *Number that would move*: rows created — predicted **2 today, target 1**. *Paired arm*: two *different* facts must still both insert, or the guard has become a global write lock on the memory table.

**T3 — What does a cache-write token cost today?** (§6.2, §6.3)
Sum `cache_creation_tokens` over 30 days of `persona_executions` and `dev_llm_spend` and price it at 1.25× the run's model input rate. *Instrument*: `llm_spend.rs`'s `group_by(conn, "model", …)` (`:186`) plus the stored bucket, against the vendor's `total_cost_usd` for the same rows. *Number that would move*: the dollar gap between the vendor total (which includes cache writes) and personas' own display estimate (which prices neither bucket) — today unmeasured, and it is the number that decides whether §6.2's `ModelPrice` is worth building. *Paired arm*: pricing `cache_read_tokens` at 0.1× must **narrow** that gap, not widen it — if the display estimate is already close because two errors cancel, the fix must land as a pair or it makes the number worse.

**T4 — How many outbound messages are silently lost?** (§7.2, §7.3)
*Instrument*: `get_notification_delivery_stats()` per-channel failure counters (`notifications.rs:1506`), plus a count of `slack_inbound_messages` rows with a non-null `error` and a null `replied_message_ts`. *Numbers that would move*: (a) the second count is the number of replies personas decided never to send — today it is terminal by construction (`slack_poller.rs:1180-1182`, `:1218-1230`), target zero for transient classes; (b) the first count is observable only while the process lives, which is itself the finding. *Paired arm*: a channel the operator disabled must not count as a failure, or an outbox will spend its retries on a decision.

**T5 — Does an FTS detach show up anywhere?** (§5.6)
Force derived damage in a test store using the module's own hermetic fault injection (`damage.rs:458-464`), then run an execution search. *Instrument*: production callers of `fts_detached` (`damage.rs:329`) and the row count the search returns. *Number that would move*: callers — **today 0, target 1**, at the executions-search read door. *Paired arm*: a healthy store must never label an answer degraded — the positive control the damage module already carries for quarantine (`:620`), restated for the read path.

## Features, ranked, with why `scope.does` admits each

`scope.does`: *"run local AI agent personas over wrapped CLIs, local-first storage, one operator per install"*, *"observe runs — cost, health, traces — and tune routing from evidence"*.

1. **A durable outbox for outbound channel delivery** (§7.2, §7.3, §7.4) → *direction*, subject `delivery-guarantees`. Admitted by **"one operator per install"**: there is no second person and no server-side replica to notice that a Slack reply never went out, and today the only evidence is an in-memory counter that dies with the process. Admitted again by **"observe runs — health"**: a delivery with no record is a health signal that cannot be observed. Ranked first because it is the one axis where the peer has a complete, small, file-backed mechanism (`outbox/` → `inflight/` → `delivered/`|`failed/`, boot requeue, atomic-create dedupe) and personas has none — and because T4's second number is already computable from a table personas owns.
2. **One price table, with cache tiers and a `verified_at`** (§6.2, §6.3) → *direction*, subject `cost-attribution`. Admitted verbatim by **"observe runs — cost… and tune routing from evidence"**: routing tuned on an estimate that prices a 400k-token cache hit identically to 400k fresh input tokens is tuned on a number the tree's own golden path already calls wrong, in a document that also writes the fix. Second because the design exists as prose with zero code (`llm-spend-accounting.md:652-655`) and exo supplies the half the prose omits — a maintained external source with a loader whose every failure rung is enumerated. T3 must run first: it decides the size.
3. **Wire the checkpoint module that already exists** (§8.4) → *direction*, subject `subprocess-lifecycle` or `agent-runtime-assembly`. Admitted by **"run local AI agent personas over wrapped CLIs"** on a machine whose repos are the operator's only copy: `git_checkpoint.rs` is written, hardened against hooks and signing, backed by a migrated table, and called by nothing, while its own header states the problem in the present tense. Third rather than first only because §8.4 is a wiring job whose scope depends on which lane claims it — the dev-tools run, the unattended lane, or both.
4. *(not proposed — recorded)* **Spill the full tool result to the exec dir before truncating** (§4.4). Real, and the directory already exists — but the audit surface it feeds is a `data-access` question about what an execution's durable artifacts are, and this study should not open it.
5. *(not proposed — recorded)* **A per-entry char cap on the memory write door** (§5.3) and **the CAS the tree already has, applied to `memories::create`** (§5.4). Both are corrections inside `agent-memory`, a subject with four applied rows in the last three days. T2 decides whether the second is real before anything is proposed.
6. *(not proposed — recorded)* **Enforce `.ai/manifest.yaml`'s `neverTouch`** (§1.2) and **route `bridge_manifest_dispatch` through `check_permission`** (§3.2). The first is one parse in a file that already opens the block; the second is two lines in a command whose sibling already does it. Both should be done, not proposed — they create no capability and close a door onto one that exists.

**Directions not proposed, and why — recorded so the next fleet-map sweep need not re-derive it.** Nothing here proposes a container or VM sandbox, a self-rebuild, a self-restart, an in-process turn loop, or a per-network worker process. `scope.does` fixes personas as a **wrapper** around vendor CLIs on the operator's own machine, and `scope.does_not` bars hosted multi-tenant surfaces. The sandbox (§8.1), the restart (§2.1), the supervisor (§2.6), the round-level registry rebuild (§3.4) and the loop itself (§4.1) are all consequences of exo *being* the harness rather than wrapping one; each is recorded as `different forces` rather than as a gap, and §8.1 carries the one reservation that is not covered by that argument.

## The inverse list — where personas is ahead

Ordered by how much of it the corpus should carry.

1. **Retrieval instead of always-inject** (§5.1) — a decay-scored greedy pack with category half-lives, an embedding blend that can only promote, access counters incremented for injected rows only so the recall does not corrupt its own signal, and **one budget constant every projecting surface must use** (§5.2), adopted after the projection was caught skipping it. exo's design note names the condition its choice needs — *"a small set of short facts"* — and then sets the cap at 200 entries of 600 characters.
2. **A typed failure taxonomy minted at the raise site and never re-read from prose** (§9.1), with a mint that returns `None` rather than guess, a `COALESCE` write that never invents a class, and `the_mint_reads_no_message` as a guard test. exo has 462 `bail!`s and exactly one named error type, minted at the one place a caller must retry.
3. **Damage classified by extended result code, with the posture chosen by what is broken rather than by who is calling** (§5.5), refused at the engine with `PRAGMA query_only` rather than at ~1,350 call sites, and with reads kept available on purpose because quarantine must be a state you can export out of.
4. **Bounds that actually bind** (§4.2, §4.3, §6.5): a non-overridable wall-clock ceiling, a stall counter that measures progress instead of counting rounds, and four spend guards — against an unbounded round default, no turn deadline and no spend guard at all.
5. **Tests that assert a persisted cost** (§6.4) — five, round-tripping through SQLite, one of which pins the rollup's exclusion semantics in the same assertion — against zero, on the arm of exo's duplicated price policy that is wrong.
6. **Reversibility expressed as a withheld enum variant** (§1.3, §8.3): `ExecutionIntegration` has only `LeaveAsBranch`, and the doc says a `Merge` variant is withheld because *"auto-merging into the user's real base branch would mutate their repo without consent"*. exo states the same principle as prose in a design document.
7. **Self-modification bounded by four independent code gates** (§1.1) — a debug-build compile gate, a mandatory approval that survived the autoapprove removal, a worktree flag whose safe value is the default, and a canonicalized cwd allowlist — against one prose invariant that three exo documents state three different ways and the canonical launcher contradicts.
8. **A heartbeat lease that refuses to trust a stored PID for liveness**, with the rejection of `flock` written into the module (§2.5), and the one PID check in the tree guarded by a process-name probe for the same reason.
9. **Routing intent in a typed column with tests on its derivation** (§7.5), where exo carries it in a `reportPrompt` string and its own design document names the coupling that creates.
10. **Loss at the budget edge that is counted and rendered** — `PackedRecall { selected, omitted }` and an explicit omission line in the prompt — against a silent `slice(-200)` (§5.3); and **a content walk that rejects symlinks by file type with a depth cap**, shipped after a measured incident in which a link to `~/.ssh` reached an export bundle (§3.3).
11. **House law with 21 custom lint rules and a census that runs before the branch leaves the machine** (§10.1, §10.2) — against a six-line `AGENTS.md` and no pre-push gate at all.
